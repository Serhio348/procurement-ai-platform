## 1. Как пользоваться документом

Начните с карты приложения и диагностики уровня. Затем проходите модули по порядку. Если можете выполнить контрольное задание без подсказки, соответствующий материал можно сократить.

Для каждого занятия используйте цикл:

1. Прочитать указанный небольшой участок кода и соседний тест.
2. Своими словами описать вход, выход и правило.
3. Предсказать результат на двух примерах.
4. Выполнить упражнение в отдельной учебной ветке.
5. Проверить результат тестом или наблюдаемым поведением.
6. Объяснить, какие слои затронуты и что может сломаться.

Большие файлы `apps/api/src/app.ts` и `apps/web/src/SpecialistApp.tsx` читайте по одному сценарию. Заучивать их целиком не нужно.

**Граница исследования.** Изучены структура репозитория, manifests всех workspace-пакетов, точки запуска, ключевые пути UI/API/SQL/MCP/LLM, авторизация, документы, фоновые задачи, инфраструктура, тестовые конфигурации и архитектурные документы. Это обзор архитектуры и учебный аудит исходников, а не доказательство отсутствия ошибок во всех строках и не повторная проверка production. Наличие модуля, успешный unit-тест и работа пользовательского сценария — три разных факта.

Все пути ниже относительны корню репозитория. Версии технологий приведены по `package.json` и инфраструктурным файлам; точные разрешённые версии npm-зависимостей фиксирует `package-lock.json`.

## 2. Технический аудит: что представляет собой приложение

### 2.1. Основная задача

Специалист создаёт профиль закупок, ищет процедуры, получает оценку релевантности, принимает решение и следит за изменениями. Для участвующих закупок система получает документы и извлекает условия с указанием источника. Входящие и Telegram помогают разбирать результаты.

Главные предметные понятия:

| Понятие | Что означает | Где изучать |
|---|---|---|
| Кабинет / workspace | Область данных конкретного пользователя: профили, решения, очереди, входящие | `apps/api/src/cabinets.ts`, `packages/db/src/specialist-store.ts` |
| Рабочий профиль | Что специалист ищет: слова, исключения, статусы, настройки слежения | `packages/contracts/src/specialist.ts`, `packages/domain/src/specialist/workspace.ts` |
| `DomainProfile` | Более общая модель направления для агентного контура | `packages/contracts/src/domain-profile.ts` |
| `SearchHit` | Кандидат из выдачи площадки; ещё не окончательное решение о релевантности | `packages/contracts/src/procurement.ts` |
| `ProcedureCard` | Нормализованная карточка внешней процедуры | `packages/contracts/src/procurement.ts`, `packages/contracts/src/source-port.ts` |
| Карточка специалиста | Проекция процедуры с состоянием работы в кабинете | `packages/contracts/src/specialist.ts`, `packages/domain/src/specialist/case.ts` |
| Решение / triage | Например, участвовать, следить, отклонить, скрыть | `packages/domain/src/specialist/triage.ts` |
| Факт и доказательство | Условие закупки плюс документ, страница и цитата, которые его подтверждают | `packages/domain/src/commercial/provenance.ts`, `packages/domain/src/commercial/trust.ts` |
| Снимок и изменение | Предыдущее состояние карточки и различия при следующем чтении | `packages/domain/src/specialist/watch.ts` |

Рабочий профиль консоли и `DomainProfile` агентного контура связаны по назначению, но не являются одним взаимозаменяемым типом.

### 2.3. Факт реализации и архитектурное намерение

| Что | Фактическое положение |
|---|---|
| Консоль | `apps/web` обращается к `apps/api`; сценарии поиска и обработки координирует API |
| Procurement MCP | API запускает дочерние процессы через stdio; есть фоновая и интерактивная линии |
| Supervisor | Реализован как `SupervisorPlanner` в `apps/agent-runtime`; обычный поиск консоли через него не проходит |
| Специализированные агенты | Реальные реализации и тесты есть; наличие capability в registry само по себе не означает наличие полного исполняемого сценария |
| Documents MCP | Сервер существует; его CLI `mcp/documents/src/main.ts` загружает fixture-каталог. Живая консоль использует библиотеку обработки документов непосредственно из `document-ingest.ts` |
| Notifications MCP | Отдельная реализация есть; текущая консоль также имеет собственный Telegram-адаптер и inbox-путь |
| База | PostgreSQL используется при заданном `DATABASE_URL`; существуют файловый и memory-режимы для других условий |
| Сбой БД | При настроенной, но недоступной БД запуск не должен тихо переключаться на другое хранилище — `persist.ts` прекращает его |
| Очередь | BullMQ обеспечивает расписание discovery при наличии Redis; без Redis используется таймер |
| PWA | Есть оболочка; API-ответы service worker не кэширует |
| CI/CD | CI с проверками и браузерными тестами есть. Автоматического production deployment в исследованном workflow нет |

Ранние документы — история решений, а не всегда актуальная инструкция. Например, `STAGE-0.md` предлагал pnpm/Turborepo и отдельные процессы, а текущий корневой `package.json` использует npm workspaces. `README.md` содержит старую отметку этапа. `docs/architecture/search-pipeline.md` описывает раннюю версию поиска. Для состояния очередей полезнее `STAGE-107.md`, но окончательный ответ всё равно проверяется по коду.

### 2.4. Что хорошо устроено и заслуживает глубокого понимания

- **Общий словарь данных:** `packages/contracts` используется на нескольких границах, поэтому схема и тип меньше расходятся.
- **Детерминированное ядро:** правила поиска, решений, доказательств и изменений вынесены в `packages/domain`; их можно проверять без сети.
- **Порты и подстановка зависимостей:** внешние сайты, модель, хранилище и часы можно заменить в тесте.
- **Изоляция кабинетов:** контекст запроса, SQL-область, профили и прогресс привязаны к workspace.
- **Проверка AI кодом:** форма ответа и подтверждение цитат проверяются отдельно от промпта.
- **Разделение долгих операций:** интерфейс получает прогресс; интерактивное чтение вынесено на отдельную линию MCP.
- **Инженерные ограничения проверяются автоматически:** ESLint, TypeScript и dependency-cruiser дополняют тесты.

Подтверждение: `AGENTS.md`, `.dependency-cruiser.cjs`, `packages/mcp-client/src/tool-policy.ts`, `apps/api/src/procurement-mcp.ts`, `packages/domain/src/commercial/trust.ts`.

### 2.5. Ограничения, которые нельзя преподавать как правильный образец

Это выводы чтения ревизии `3895df2`. Здесь описаны основания и риски, а не утверждение о воспроизведении каждого случая на production.

| Наблюдение | Подтверждение | Практический смысл |
|---|---|---|
| Получение документов выбирает источник по `card.live ? "goszakupki_by" : "fixture"` | `apps/api/src/document-ingest.ts`, `createProcurementDocumentIngest` | Маршрутизация не учитывает БУТБ; успешный поиск ещё не доказывает работоспособность «Участвовать → документы» |
| Discovery не использует возвращённый `hasMore`, затем вызывает `markDiscovered` | `apps/api/src/app.ts`, `discoveryPass` | При неполном чтении нельзя считать интервал полностью обработанным; есть риск пропуска хвоста |
| Ошибка источника превращается в пустую страницу с `hasMore: false` | `apps/api/src/procurement-search.ts` | Другие источники продолжают работу, но вызывающий код теряет различие между «пусто» и «не удалось» |
| Health опрашивает интерактивную линию MCP | `apps/api/src/main.ts`, `sourcesProbe` | Реестр интерактивного процесса не подтверждает состояние фонового |
| При ошибке `sourcesProbe` список из конфигурации остаётся в `sources`, а ошибка идёт в `degraded` | `apps/api/src/app.ts`, `/api/health` | Читать нужно весь результат health; `sources` не всегда подтверждён свежим успешным опросом |
| Ограничение БУТБ по времени проверяется между чтениями страниц | `mcp/procurement/src/butb-source.ts`, `search` | Это мягкий бюджет; начатый HTTP-запрос и ожидание в общей очереди могут увеличить общее время |
| `app.ts` и `SpecialistApp.tsx` объединяют много обязанностей | Сами файлы | Реальный service layer частично находится в больших функциях, а не в отдельных каталогах controllers/services |

Первый разумный пакет улучшений: полнота discovery и различение ошибок источников; второй — маршрутизация документов; третий — сквозной сценарий БУТБ и диагностика обеих линий. Они требуют отдельного решения и тестов. Учебный план не предполагает переписывания приложения ради архитектурной схемы.

## 3. Технологический стек и глубина изучения

**A — обязательно:** нужно для уверенного чтения и обычных изменений. **B — желательно:** изучать при развитии соответствующего блока. **C — обзорно:** понимать границу и назначение; детали отложить.

«Глубоко» здесь означает уметь диагностировать и менять механизм, а не изучать внутренности библиотеки.

### 3.1. Язык, сборка, интерфейс

| Приоритет / технология | Где | Зачем именно здесь | Что изучить и насколько | Что будет непонятно без этого |
|---|---|---|---|---|
| A · JavaScript ES2023 | Все `src/`, `tsconfig.base.json` | Один язык браузера и сервера | Функции, объекты, массивы, Map/Set, замыкания, ошибки, модули — глубоко | Преобразования выдачи и управление состоянием |
| A · TypeScript 5 | Все manifests и `tsconfig*` | Проверяет совместимость множества слоёв | Unions, interfaces, narrowing, generics, `unknown`, readonly, branded types, optional fields — глубоко | Почему нельзя передать любой ID или забыть отсутствующее поле |
| A · Node.js 22+ | Корневой `package.json`, API и MCP | HTTP, процессы, файлы, криптография | Event loop, Promise, timers, Buffer, process.env, AsyncLocalStorage — рабочее владение | Почему фон может мешать запросам и как передаётся контекст |
| A · npm workspaces, ESM | `package.json`, manifests пакетов | Общие пакеты в одном репозитории | Скрипты `-w`, exports, `.js` в TS-импортах, lockfile, project references | Отличия запуска теста по src от запуска через собранный пакет |
| A · Zod 4 | `packages/contracts`, HTTP/MCP/LLM-адаптеры | Проверяет данные, которые TypeScript не может гарантировать во время исполнения | `parse`, `safeParse`, `infer`, object/enum/union, strict/optional/default — глубоко | Почему внешний JSON нельзя считать правильным по объявленному типу |
| A · React 19, React DOM | `apps/web/src/main.tsx`, компоненты | Интерактивная консоль с профилями и списками | Props, JSX, state, effects, refs, context, keys, controlled inputs — глубоко | Повторные рендеры, несохранённые правки, старые ответы запросов |
| A · React Router 7 | `apps/web/src/main.tsx` | URL и доступ к экранам приложения | Routes, навигация, параметры, guard — рабочий уровень | Почему перезагрузка должна сохранять доступ к нужному экрану |
| A · HTML/CSS | `apps/web/src/styles.css`, `shell/`, формы | Собственный UI без большого UI-framework | Flex/Grid, media queries, семантика форм, focus, accessibility — рабочий уровень | Мобильная компоновка и поведение клавиатуры |
| A · HTTP / Fetch API | `apps/web/src/api/`, API-адаптеры LLM | Команды и данные между процессами | Методы, статус, headers, JSON, cookies, origin, abort/timeout — глубоко | Различия 401, 403, 429, сетевого отказа и пустого результата |
| B · Vite 6, React plugin | `apps/web/vite.config.ts` | Dev server и production bundle | Proxy `/api`, alias, build, dist, публичные переменные — рабочий уровень | Почему Vite нужен в разработке, а nginx обслуживает сборку |
| B · PWA / service worker | `apps/web/public/sw.js`, manifest | Устанавливаемая оболочка и запуск при проблемах сети | Жизненный цикл и cache-first/network-first — обзор плюс чтение кода | Почему нельзя показывать старое решение из offline-кэша |

### 3.2. Backend, данные и внешние системы

| Приоритет / технология | Где | Проблема и выбор проекта | Глубина изучения | Без этого |
|---|---|---|---|---|
| A · Fastify 5 | `apps/api/src/app.ts`, `auth/register.ts` | HTTP-сервер с hooks и тестируемой сборкой приложения | Маршруты, lifecycle, request/reply, errors, `inject` — глубоко | Нельзя проследить проверку прав и выполнение команды |
| A · PostgreSQL 16 | `packages/db/src/`, `infra/docker-compose.yml` | Постоянные данные кабинетов, связи и ограничения | SQL, JOIN, индексы, UNIQUE/FK, транзакции, JSONB — глубоко | Потеря данных, дубли и медленные списки |
| A · Drizzle ORM + pg | `packages/db/src/client.ts`, `schema.ts`, `specialist-store.ts` | Типизированные SQL-запросы при явных SQL-операциях | Схема, where/join, transaction, migrations, pool — рабочее владение | Схема TS и реальная БД начнут расходиться |
| A · Cookie sessions, crypto | `apps/api/src/auth/` | Управляемые сессии и отзыв доступа | HttpOnly/SameSite/Secure, хеш токена, salt+scrypt, роли — глубоко по потоку | Ошибочное представление, что скрытая кнопка защищает API |

## 4. Реальная архитектура и движение данных

### 4.1. Основной контур консоли

```text
Специалист
  ↓
React SPA — apps/web
  ↓ Fetch / JSON / cookie
Vite proxy (разработка) или nginx (сервер)
  ↓ /api/*
Fastify — apps/api
  ├── Auth hook → principal → workspace → AsyncLocalStorage
  ├── HTTP-контракт Zod
  └── Прикладной сценарий в app.ts и модулях API
        ├── packages/domain → правила, score, diff, проверка фактов
        ├── packages/db → Drizzle/pg → PostgreSQL
        ├── procurement-mcp → дочерний MCP по stdio
        │     └── procurement tools → source registry → адаптер сайта
        │           ├── goszakupki.by: HTTP + HTML
        │           └── БУТБ: JSF-сессия + XML/HTML
        ├── LLM-адаптеры API → Chat Completions → проверка ответа
        ├── document-ingest → библиотека документов → OCR/LLM
        │     └── BlobStore → диск / S3 (MinIO)
        └── inbox / Telegram / SMTP

Redis/BullMQ либо таймер
  ↓
runDiscovery → кабинеты последовательно → мониторинг + поиск профилей
  ↓
те же доменные правила, адаптеры и хранилища
```

Опорные файлы: [main.ts API](apps/api/src/main.ts), [app.ts](apps/api/src/app.ts), [вызовы UI](apps/web/src/api/specialist.ts), [MCP-процесс](apps/api/src/procurement-mcp.ts).

Здесь API и backend — не два независимых сервиса: Fastify является HTTP-входом в backend-процесс. «Services» — функции и модули внутри этого процесса. Это модульное приложение с выделенными MCP-процессами, а не набор независимо развёрнутых микросервисов для каждой папки.

### 4.2. Отдельный агентный контур

```text
Структурированный SupervisorRequest
  ↓
SupervisorPlanner
  ├── проверяет область и конфликты правил
  ├── запрашивает план у модели
  └── валидирует SupervisorPlan
        ↓
ContextCompiler — отдельный реализованный компонент
        ↓
MinimalAgentContext + разрешённые инструменты
        ↓
Специализированные классы агентов
        ↓
ToolPolicyGate → typed MCP client → tools
```

Это схема назначения реализованных компонентов. Она не означает, что в текущем API есть универсальный исполнитель всех `SupervisorPlan.steps`. Для console search точка входа — `app.ts`, а не `SupervisorPlanner`.

Источники: `apps/agent-runtime/src/supervisor/supervisor.ts`, `context/compiler.ts`, `agents/*/agent.ts`, `registry/capabilities.ts`, а также зависимости `apps/api/package.json`.

В registry присутствуют определения `auction_analysis` и `risk_analysis`, но наличие записи и permissions не заменяет отдельную реализацию агента и её подключение. Аналогично имя `memory.get` в перечне допустимых tools не доказывает, что запущен Memory MCP.

### 4.3. Пять сценариев, которые нужно уметь проследить

**Вход.** Форма вызывает auth API → Zod проверяет запрос → `AuthDirectory` проверяет пароль → сервер создаёт случайный токен сессии → браузер получает cookie → следующие запросы находят пользователя по хешу токена → сервер проверяет роль и кабинет. JWT здесь не является основным механизмом. Файлы: `apps/web/src/auth/`, `apps/api/src/auth/register.ts`, `postgres-directory.ts`, `cookie.ts`, `token.ts`, `password.ts`.

**Поиск профиля.** UI отправляет `profileId` → backend читает сохранённый профиль → `fetchProfileHits` получает план и выдачу, при необходимости добавляет поисковые термы → поиск расходится по разрешённым источникам → кандидаты объединяются → доменные фильтры и чтение карточек → правила и, для спорных случаев, модель → результат сохраняется по профилю → UI читает прогресс. Числовую релевантность считает код; модель может дать смысловой вердикт, который код проверяет и переводит в результат. Файлы: `app.ts`, `profile-search-query.ts`, `procurement-search.ts`, `search-review.ts`, `packages/domain/src/search/`.

**Чтение списка.** Запрос вкладки → кабинет из principal → `cabinets.listCases` / store → SQL с областью workspace и пагинацией → нормализованный ответ → Zod на клиенте → React state → список. Список может содержать сокращённые карточки; деталь загружает полную. Файлы: `persist.ts`, `packages/db/src/specialist-store.ts`, `apps/web/src/procurements/ProcurementDetailApp.tsx`.

**Участвовать и читать документы.** Решение сохраняется → начинается фоновый ingest → MCP получает список/байты → вычисляется hash → файл кладётся в BlobStore → архив раскрывается, текст извлекается → при необходимости OCR → правила извлекают доступные условия → модель дочитывает выбранные страницы → цитаты и числа проходят проверку → карточка обновляется. Текущая маршрутизация БУТБ в ingest имеет ограничение из раздела 2.5. Файлы: `document-ingest.ts`, `mcp/documents/src/routing-extractor.ts`, `packages/domain/src/commercial/`.

**Мониторинг.** Планировщик запускает проход → перечитываются отслеживаемые карточки → новый снимок сравнивается со старым → изменения превращаются во входящие → Telegram отправляет уведомления с дедупликацией. Слежение за принятой закупкой и поиск новых по профилю — разные действия. Файлы: `discovery-queue.ts`, `card-watch.ts`, `packages/domain/src/specialist/watch.ts`, `apps/api/src/telegram.ts`.

### 4.4. Архитектурные решения: механизм → цель → концепция

| Как работает | Зачем | Концепция и подтверждение |
|---|---|---|
| UI вызывает API, а SQL находится на сервере | Общие права, валидация и сохранение независимо от браузера | Client/server; `apps/web/src/api/`, `apps/api/src/app.ts` |
| Общие схемы экспортируют runtime-валидатор и TS-тип | Меньше расхождений в данных между слоями | Contract-first, DTO, schema validation; `packages/contracts/src/` |
| Домен получает обычные значения и не делает I/O | Правила можно повторить и протестировать без сайта/БД | Functional core; `packages/domain`, `.dependency-cruiser.cjs` |
| `main.ts` создаёт реализации и передаёт их через options | Выбирать live/fixture, SQL/disk, модель/fake | Ручная dependency injection, composition root |
| CabinetRegistry/AuthDirectory/BlobStore скрывают способ хранения | Сценарий не должен знать SQL или S3-команды | Ports/adapters, repository-подобные интерфейсы |
| Fastify hooks создают principal и контекст кабинета | Не копировать проверку пользователя в каждый обработчик | Middleware/lifecycle; `auth/register.ts`, `app.ts` |
| ALS переносит кабинет через async-цепочку | Одновременные запросы не должны читать один общий mutable workspace | Request scope; `app.ts` |
| SQL-транзакции задают workspace context, записи используют lock | Согласованность и изоляция при конкуренции | Unit of work, RLS, advisory lock; `workspace-scope.ts`, SQL-миграции |
| Карточка площадки и её состояние в кабинете различаются | Одна процедура может интересовать разных специалистов | Разделение общей сущности и пользовательской проекции; `schema.ts` |
| API вызывает источник через MCP, затем адаптер | Изменение HTML площадки не должно менять UI или правила | Anti-corruption layer, adapter; `source-port.ts`, `source-registry.ts` |
| Глобальный feature flag и список кабинетов проверяются отдельно | Возможность ограниченного пилота | Feature gating; `main.ts`, `decision-memory.ts` |
| Часы, fetch и порты передаются параметрами | В тестах можно воспроизвести истечение срока и отказ сети | Test seams; `butb-http.ts`, `search-intent.ts` |
| Прогресс содержит profileId/runId; UI защищается от поздних ответов | Старый поиск не должен затереть новый | State machine, ownership/generation; `search-progress.ts`, `apps/web/src/procurements/ProcurementsApp.tsx`, `MyProcurementsApp.tsx` |
| Документ получает SHA-256 и отдельные метаданные | Повторное содержимое не нужно хранить как новый файл | Content-addressed storage; `blobs.ts`, `object-store.ts` |
| Изменения имеют identity/dedupe, решения сохраняются | Повторная обработка не должна повторять пользовательский эффект | Idempotency; `watch.ts`, `telegram-store.ts`, `specialist-store.ts` |

RLS следует изучать вместе с SQL-политиками и ролью соединения. Сам вызов `set_config` не доказывает, что любая роль БД ограничена политиками: привилегии роли и bypass тоже важны.

### Чего не нужно приписывать проекту

- **Embeddings, vector DB, pgvector, ANN-поиск:** исполняемый конвейер не обнаружен. Глубоко изучать сейчас не требуется.
- **Векторный RAG:** не обнаружен. Здесь есть отбор страниц и передача текста модели — это работа с извлечённым контекстом, но не основание описывать отсутствующий векторный индекс.
- **`documents.search`:** в `mcp/documents/src/server.ts` это поиск подстроки по уже извлечённым страницам одного blob, а не семантический поиск по всей базе знаний.
- **LLM token streaming:** рассмотренные адаптеры отправляют `stream: false`. Прогресс UI передаётся polling, его не нужно путать со streaming ответа модели.
- **WebSocket/SSE как основной UI-канал:** такого пути в исследованных модулях нет.
- **Redux/Zustand/React Query:** не являются используемым слоем состояния в текущих manifests и UI.
- **JWT/OAuth как основа входа:** вместо них используются серверные сессии и cookie.
- **LangChain/LangGraph:** агентный runtime написан собственными классами и портами.
- **Kubernetes, Kafka, GraphQL, Next.js/SSR, Terraform:** не нужны для понимания текущего приложения.
- **Полный event sourcing / общий production outbox dispatcher:** схема событий или таблица `notificationOutbox` сами по себе этого не подтверждают. Текущий inbox/Telegram-путь нужно читать отдельно.
- **React ErrorBoundary:** обработка API-ошибок подтверждена; отдельный общий компонент ErrorBoundary в исследованном UI не найден.

| Направления исключений | Недавние решения/отказы профиля | Фразы проверяются на реальных отказах и принятых закупках | `assistant-directions.ts`, `packages/domain/src/assistant/directions.ts` |

### 6.2. Что изучить глубоко

1. **Структура ответа не равна истине.** JSON с полями по схеме всё ещё может содержать выдуманную цитату.
2. **Числовой score и уверенность модели различаются.** Confidence не является измеренной вероятностью, а model verdict не заменяет арифметику доменного scorer.
3. **Контекст выбирает приложение.** Карточка, релевантные лоты и страницы передаются явно; модель не читает вашу PostgreSQL сама.
4. **Модель не является владельцем инструментов.** В текущих сценариях код вызывает MCP; agent permissions ограничены `ToolPolicyGate`.
5. **Стоимость и задержка — часть алгоритма.** Общий budget модели на прогон, предел страниц и timeouts влияют на результат.
6. **Неопределённость — нормальное состояние.** `needs_human` лучше неподтверждённого положительного решения.
7. **Память решений не является обучением весов.** Приложение сохраняет решения и использует их как данные; это не fine-tuning.

Приоритет обучения: JSON и async → схемы → правила поиска → HTTP-порт модели → проверка результата → контекст → агентный runtime. Математику обучения нейросетей, GPU и устройство трансформеров можно отложить.

## 7. Ваш стартовый уровень

По репозиторию нельзя определить ваш уровень программирования: часть кода создавалась с помощью AI. Сложный проект не является доказательством того, что его владелец самостоятельно владеет всеми технологиями.

По разговору видно знакомство с задачей закупок, профилями, мониторингом, кабинетами и смыслом ограниченного пилота. Это полезная предметная база, но не оценка навыков TypeScript или SQL.

| Уже можно считать знакомым | Зачем нужны поиск, слежение, исключения, карточка, документы; какие ошибки недопустимы для специалиста |
| Нужно закрепить | Различие сайта-источника, нашего API и UI; что такое фоновый проход; отличие найденного кандидата от подходящей закупки |

## 9. Учебная программа

Каждый модуль заканчивается проверяемым результатом. Упражнения выполняются в отдельной учебной ветке/копии, на fixture-данных и отдельной тестовой БД. Предлагаемые изменения — задания, а не уже внесённые функции продукта.

Для начинающего «прочитал объяснение» не считается завершением: нужно самостоятельно выполнить практику и объяснить результат.

### Модуль 1 — найти маленькое правило и проверить его

**Что изучить:** устройство npm workspace; `git status`, `git diff`, отдельная ветка; функции, `const`, `if`, цикл, массив, объект, Set; структура теста `describe/it/expect`.

**Зачем:** научиться читать и менять приложение с небольшого участка, результат которого не зависит от сайта или модели.

**Где:** `packages/domain/src/specialist/triage.ts` и `triage.test.ts`; корневой `package.json`.

**Практика:** для `partitionHitsByDecision` составить три входа: нет принятых решений, часть кандидатов уже решена, все кандидаты уже решены. Сначала записать ожидаемый результат, затем добавить один отсутствующий содержательный тест в существующий файл. Если сценарий уже покрыт, объяснить его тест вместо дублирования.

## 10. Объяснение концепций на вашем коде

Ниже — маленькие входы в сложные механизмы. Код в примерах учебный и упрощённый; это не готовые патчи и не замена существующим контрактам.

### 10.1. Dependency Injection

**Где:** `apps/api/src/object-store.ts`, `document-ingest.ts`; `createProcurementSearchHits` в `procurement-search.ts`.

**Что происходит:** сценарий получает объект с нужными методами. Для него важна способность прочитать файл или вызвать tool, а не конкретная реализация.

**Почему:** тесту не нужен MinIO, а приложению не нужно менять бизнес-правило при переходе с диска на S3.

**Знать до чтения:** interface, объект с функциями, Promise.

```ts
interface Store {
  get(hash: string): Promise<Uint8Array | undefined>;
}
async function readDocument(store: Store, hash: string) {
  return store.get(hash);
}
const fake: Store = { get: async () => new Uint8Array([1, 2]) };
```

**Задание:** найти все реализации `BlobStore`, объяснить, кто выбирает нужную, и проверить отсутствующий blob через fake.

### 10.2. Schema validation и DTO

**Где:** `packages/contracts/src/source-port.ts`, `apps/web/src/api/specialist.ts`.

**Что происходит:** полученный JSON превращается в доверенное для дальнейшего кода значение только после проверки формы.

**Почему:** сеть, старый клиент и ответ модели не подчиняются вашему TypeScript-компилятору.

**Знать:** JSON, unknown, тип против значения.

```ts
const Answer = z.object({ hits: z.array(z.string()) });
const raw: unknown = JSON.parse('{"hits": 7}');
const checked = Answer.safeParse(raw); // success === false
```

**Задание:** сравнить повреждённый ответ с корректным `{ hits: [] }`; объяснить, почему это разные состояния.

### 10.3. Чистая доменная функция

**Где:** `packages/domain/src/specialist/triage.ts`.

**Что происходит:** `partitionHitsByDecision` разделяет данные без HTTP и SQL.

**Почему:** правило «не предлагать уже решённое» одинаково важно при ручном поиске и в фоне.

**Знать:** коллекции, побочный эффект, одинаковые входы/выходы.

```ts
function unseen(ids: readonly string[], decided: ReadonlySet<string>) {
  return ids.filter((id) => !decided.has(id));
}
```

**Задание:** указать, где вызывающий слой получает `decided`, а где применяется само правило.

### 10.4. Middleware и request scope

**Где:** `apps/api/src/auth/register.ts`, `app.ts`: hooks и `cabinetAls`.

**Что происходит:** сначала устанавливается principal, затем кабинет; downstream-функции получают контекст своей async-цепочки.

**Почему:** глобальная переменная `currentUser` могла бы смешать одновременные запросы.

**Знать:** async, callbacks, authentication, область видимости.

```ts
const scope = new AsyncLocalStorage<{ workspaceId: string }>();
await scope.run({ workspaceId: "cabinet-A" }, async () => {
  await readSomething();
  return scope.getStore()?.workspaceId;
});
```

**Задание:** нарисовать две независимые цепочки A и B; найти, где scope передаётся в фоновую задачу.

### 10.5. Repository и транзакция

**Где:** `packages/db/src/specialist-store.ts`, `workspace-scope.ts`.

**Что происходит:** несколько связанных действий выполняются через store в одной SQL-транзакции, при необходимости под lock кабинета.

**Почему:** нельзя сохранить часть пользовательского решения и оставить связанные данные в противоречивом состоянии.

**Знать:** SQL, await, commit/rollback, идентификаторы.

```ts
await db.transaction(async (tx) => {
  await saveDecision(tx, decision);
  await updateCard(tx, card);
}); // завершение обоих шагов или rollback
```

**Задание:** найти реальную границу транзакции; отличить её от очереди Promise в `persist.ts`. Это два разных уровня защиты.

### 10.6. Защита от устаревшего ответа

**Где:** `apps/web/src/procurements/ProcurementsApp.tsx`, `MyProcurementsApp.tsx`, `apps/api/src/search-progress.ts`.

**Что происходит:** результат принадлежит определённому запросу/прогону. Более старый ответ не должен перезаписать новый экран.

**Почему:** сеть может завершить запрос B раньше запроса A.

**Знать:** closure, useRef, Promise, ownership.

```ts

async function reload() {

  const rows = await loadRows();
  if (mine !== generation) return;
  showRows(rows);
}
```

**Задание:** управляемыми Promise завершить два запроса в обратном порядке; проверить, какой результат показан.

### 10.11. События и идемпотентность

**Где:** `packages/domain/src/specialist/watch.ts`, `packages/db/src/telegram-store.ts`.

**Что происходит:** изменение создаёт идентифицируемое событие; обработка повторного события не должна повторять эффект.

**Почему:** job, HTTP-запрос или отправка могут быть повторены после сбоя.

**Знать:** equality, Set/UNIQUE, persistence, snapshot.

```ts
const eventKey = identifyTransition(before, after);
if (await sentStore.has(eventKey)) return;
await deliver(event);
await sentStore.mark(eventKey);
```

Этот учебный фрагмент показывает намерение, но имеет окно между `deliver` и `mark`: сбой в нём может привести к повтору. Именно поэтому слово «дедупликация» не следует автоматически переводить в гарантию exactly-once.

**Задание:** определить, какой повтор исключает текущий store и какие сбои требуют дополнительного протокола доставки.

### 10.12. Кэш и single-flight

**Где:** `butb-source.ts` — TTL карточки и позиции; `persist.ts` — Promise открытия кабинета.

**Что происходит:** TTL повторно использует уже полученный результат; single-flight объединяет одновременные запросы одного ещё не готового результата.

**Почему:** без первого возникают лишние чтения сайта; без второго два запроса могут создать два объекта состояния одного кабинета.

**Знать:** Map, Promise, время жизни, invalidation.

```ts
const opening = new Map<string, Promise<Cabinet>>();
function open(id: string) {
  const known = opening.get(id);
  if (known) return known;
  const pending = loadCabinet(id);
  opening.set(id, pending);
  return pending;
}
```

**Задание:** объяснить, что делать с rejected Promise и почему эта учебная функция ещё не описывает все правила production-кэша.

### 10.13. React effect и polling

**Где:** `apps/web/src/auth/AuthSession.tsx`, `SpecialistApp.tsx`.

**Что происходит:** UI периодически читает состояние сервера и останавливает таймер при завершении эффекта.

**Почему:** поиск продолжает работать после HTTP-ответа и без постоянного соединения браузера.

**Знать:** lifecycle, effect dependencies, async errors.

```tsx
useEffect(() => {
  const timer = setInterval(() => void refresh(), 3000);
  return () => clearInterval(timer);
}, [refresh]);
```

**Задание:** объяснить, почему нестабильная ссылка `refresh` перезапускает effect и как существующий UI отличает сбой обновления от пустого списка.

### 10.14. Файл как содержимое и файл как запись

**Где:** `apps/api/src/blobs.ts`, `object-store.ts`, `packages/db/src/schema.ts`.

**Что происходит:** байты адресуются hash, а имя, URL, статус распознавания и принадлежность карточке — метаданные.

**Почему:** один файл может встречаться в нескольких процедурах; одинаковая ссылка может позже отдавать новые байты.

**Знать:** bytes, hash, storage key, DB row.

```text
URL → байты → SHA-256 → blobs/<hash>
                 ↘ метаданные и связь с карточкой в БД
```

**Задание:** описать два случая: другое имя при тех же байтах; тот же URL при изменившихся байтах. Где появится новая версия?

## 13. Приоритеты и итоговый roadmap

### Уровень 1 — фундамент

**Модули 1–3.** Начать с знакомого правила «не предлагать уже решённое», затем перейти к типам и ожиданию внешнего ответа.

**Готовность:** вы самостоятельно объясняете функцию, пишете meaningful тест и различаете тип, JSON, runtime-проверку и Promise.

### Уровень 2 — понимание приложения

**Модули 4–7.** UI → API → сессия → кабинет → PostgreSQL.

**Готовность:** можете провести значение поля профиля от ввода до сохранения и обратно, найти проверку права и область данных. Можете сделать маленькую UI-правку и обосновать, нужен ли новый endpoint.

### Уровень 3 — самостоятельная разработка

**Модули 8–11 и 14**, с постепенным освоением тестирования из модуля 17.

**Готовность:** можете воспроизвести гонку, отличить неполный поиск от пустого, изменить доменное правило и защитить его регрессией, добавить поведение за существующим портом.

Для упражнений с мониторингом документов сначала пройти модуль 13; для мониторинга только статуса/срока достаточно snapshots и знаний хранения.

### Уровень 4 — AI и продвинутая архитектура

**Модули 12–13, 15–16.** Сначала реальные LLM-порты консоли и доказательства, затем помощник и отдельный агентный runtime.

**Готовность:** вы можете обосновать вход модели, проверить плохой ответ, ограничить инструменты и стоимость, показать человеку источник факта.

RAG с embeddings и vector search в этот уровень сейчас не включён: для существующего конвейера он не требуется.

### Уровень 5 — production

**Модули 17–18.** Проверяемый пользовательский сценарий, сборка, deployment, диагностика и восстановление.

**Готовность:** можете подготовить изменение к выпуску, объяснить проверенные границы и выполнить обновление на учебном стенде с подтверждённой версией.

### Реалистичный ритм

Начальный режим: три занятия по 60–90 минут в неделю плюс одно короткое повторение. На один модуль выделять столько занятий, сколько нужно для контрольного задания: простым может хватить 1–2, сложным потребуется несколько.

## 14. Рабочие команды и правила практики

Все команды ниже выполняются из корня репозитория, кроме явно указанного workspace.

```bash
# Обычная установка воспроизводимых npm-зависимостей
npm ci

# Сборка workspace-пакетов TypeScript
npm run build

# API + Vite для разработки
npm run web

# Один доменный тест
npx vitest run packages/domain/src/specialist/triage.test.ts

# Тесты backend/domain/MCP И отдельный web-suite
npm test

# Все обязательные проверки репозитория
npm run verify

# Отдельная сборка интерфейса
npm run build -w @procurement/web

# Архитектурные зависимости
npm run arch

# Оценка правил поиска на подготовленных данных
npm run evaluate:search

# Браузерный сценарий
npm run test:e2e
```

Перед `npm run web` в отдельной учебной копии проверить конфигурацию: fixture-источник, отключённый discovery, отсутствие рабочих ключей и адресов БД/Redis/S3. `PROCUREMENT_SOURCE_MODE=fixture` сам по себе не отключает все остальные интеграции.

`loadDotEnv` в `apps/api/src/load-env.ts` не перезаписывает уже заданные process env. Это нужно учитывать при диагностике «я изменил .env, а поведение осталось». CLI миграций требует доступный `DATABASE_URL`; не предполагается, что каждый CLI читает `.env` так же, как API.

Для PostgreSQL-практики нужны отдельная БД и `TEST_DATABASE_URL`. Для миграций этой БД `DATABASE_URL` указывает туда же. Для Redis-тестов проверьте условия запуска в соответствующем тесте: наличие Redis-сервиса само по себе не гарантирует включение всех opt-in проверок.

Перед Playwright может понадобиться установка его браузера: `npx playwright install chromium`. Конфигурация использует отдельные порты `3199/5199`; убедитесь, что локально повторно используемый процесс действительно соответствует тестовой конфигурации.

**Как сдавать практическую работу:**

```text
Сценарий:
Ожидание:
Фактическое поведение:
Где находится правило:
Какие границы затронуты:
Изменение:
Чем проверено:
Что не проверено:
```

Такой формат важнее большого комментария «всё работает».

## 15. Выпускные практические работы

### Работа A — изменение UI без изменения бизнес-правила

Показать понятный дополнительный индикатор профиля на основе существующих данных.

**Приёмка:** корректны пустой профиль, переключение и сохранение; нет лишнего запроса к LLM; компонентный тест проверяет видимое поведение.

### Работа B — объяснить и исправить ошибку отбора

Выбрать один пример ложного совпадения по вашему предметному направлению. Найти, вызван ли он retrieval, нормализацией, правилом карточки или модельным review.

**Приёмка:** есть воспроизводимая fixture-регрессия, не сломан противоположный пример, объяснено изменение precision/recall. Нельзя ограничиться удалением неудобного примера из evaluation.

### Работа C — неполный фоновый поиск

Спроектировать представление успешного полного ответа, частичного ответа и отказа источника. Определить, когда допустимо продвигать watermark и что сохраняется для продолжения.

**Приёмка:** сначала тест на непрочитанный хвост; отказ БУТБ не теряет результаты goszakupki; повтор проходит без дублей; обновление состояния не обещает полноту, которой нет. Это отдельная инженерная задача, а не упражнение начинающего на рабочей БД.

### Работа D — сквозное добавление источника к документам

На тестовых портах пройти «карточка БУТБ → участвовать → get_documents → download → файл → статус обработки».

**Приёмка:** правильный `sourceId` во всех вызовах, scoped запись в нужный кабинет, корректный отказ при недоступности документа, другой источник не сломан. Проверка поиска без ingest не считается выполнением этой работы.

### Работа E — подтверждённое условие из документа

Добавить или улучшить извлечение одного условия на небольшом fixture-документе.

**Приёмка:** есть источник и страница, неверная цитата/число отвергаются, повторное чтение не дублирует файлы, модель необязательна для воспроизведения теста.

### Работа F — выпуск на учебный стенд

Подготовить одну из предыдущих работ к обновлению приложения.

**Приёмка:** diff понятен, проверки выполнены с отмеченными skipped, UI собран отдельно, миграции оценены, версия процесса подтверждена, пройден целевой сценарий, описан способ восстановления.

## 16. Что пока можно отложить

| Можно отложить | Почему | Когда вернуться |
|---|---|---|
| Embeddings, ANN, vector database | Текущий поиск так не устроен | При обоснованной задаче семантического поиска по корпусу |
| LangChain/LangGraph | Здесь собственные порты и runtime | Если появится конкретная потребность и сравнительный эксперимент |
| Обучение нейросетей, GPU, fine-tuning | Используются внешние inference API | При задаче собственной модели с измеримым выигрышем |
| Kubernetes и service mesh | Текущий deployment — VPS, systemd, Compose | При реальной необходимости нескольких экземпляров/кластерного управления |
| Redis как универсальное хранилище бизнеса | В этом приложении он обслуживает очередь/расписание | Только при отдельном архитектурном решении |
| Тонкости внутреннего устройства JSF | Нужен протокол конкретного сайта | При изменении поведения БУТБ, которое нельзя объяснить текущими fixtures |
| Реализация PDF/OLE-декодера с нуля | Уже есть библиотеки и адаптеры | При воспроизводимом дефекте extraction конкретного формата |
| Продвинутый type-level TypeScript | Основную пользу дают явные типы и схемы | Когда понятна задача, которую простые типы не выражают |
| Переписывание API на новый framework | Это не условие понимания существующего приложения | Только по измеримой инженерной причине |
| Полная история всех STAGE-документов подряд | Многие описывают промежуточное поведение | Читать этап, относящийся к изучаемому механизму |

Откладывать нельзя: основы безопасности кабинетов, проверку внешних данных, сохранность решений, различие частичного результата и ошибки. Это часть обычной разработки, а не факультатив «после запуска».

## 17. Итоговый набор компетенций

Для самостоятельного развития этого приложения вы должны уметь:

- [ ] Объяснить предметную цепочку профиль → кандидат → карточка → решение → мониторинг.
- [ ] Найти реализацию поведения по UI-действию и пройти до данных/внешнего источника.
- [ ] Читать и изменять строгий TypeScript без обхода проверок через `any`.
- [ ] Различать контракт, runtime-валидацию и бизнес-инвариант.
- [ ] Написать чистое доменное правило и содержательный тест.
- [ ] Управлять React state, формой, загрузкой и устаревшим ответом.
- [ ] Добавить API-поведение с проверкой данных, роли и области кабинета.
- [ ] Читать SQL/Drizzle, понимать транзакцию, ограничения и миграцию.
- [ ] Доказать, что изменение переживает reload/новый процесс.
- [ ] Сохранить идентичность workspace/profile/run/source/card на всём пути.
- [ ] Различать retrieval, score, model review и human decision.
- [ ] Проверять полноту поиска и корректность продвижения watermark.
- [ ] Диагностировать MCP по процессу, env, tools, очереди и ответу адаптера.
- [ ] Понимать session-based источник и проверять последовательность запросов.
- [ ] Подключать LLM через ограниченный порт и обрабатывать плохой ответ.
- [ ] Проверять AI-факт по документу, странице, цитате и значению.
- [ ] Отличать файл, blob, извлечённый текст и подтверждённое условие.
- [ ] Проектировать повтор фоновой задачи без потери данных и очевидных дублей.
- [ ] Различать реализованный агент, definition capability и фактическую точку запуска.
- [ ] Выбирать unit/integration/UI/e2e/live-проверку под конкретный риск.
- [ ] Читать технический JSON-лог и связывать события по идентификаторам.
- [ ] Выпускать изменение с проверкой сборки UI, процесса API и целевого сценария.
- [ ] Честно указывать непроверенные границы вместо вывода «всё работает».

Первый практический рубеж — самостоятельно сделать маленькое изменение в профиле/UI или доменном правиле. Второй — провести изменение через API и сохранение. Третий — исправить воспроизводимый дефект поиска/документов с регрессией. Владеть всей платформой сразу для начала полезной работы не требуется.
