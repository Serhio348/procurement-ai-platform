### [x] R02 · P1 · «Открыть карточку» само подтверждает релевантность и добавляет чужой профиль

**Воспроизведено.** `resolve` с `action: open` устанавливает `foundAs: match`, присоединяет текущий активный профиль и добавляет карточку в его очередь. Это навигация, не явное решение «подходит». Кандидат из профиля A, открытый при активном B, получил оба `profileIds` и `match` без проверки B.

- Где: [app.ts:1679–1690](apps/api/src/app.ts#L1679), [SpecialistApp.tsx:353–359, 580–584](apps/web/src/SpecialistApp.tsx#L353).
- Последствие: даже посторонний котёл может стать подтверждённым совпадением только после просмотра.
- Исправление: отделить просмотр от принятия; сохранять профиль происхождения review; ввести явные действия «Подходит / Не подходит / Перепроверить».
- Приёмка: открытие не меняет вердикт, профильные связи и решение пользователя; принятие требует отдельной команды.

### [x] R05 · P1 · Сохранённые review-кандидаты больше не перепроверяются

**Воспроизведено.** Первый запуск вернул `needs_human`; порт проверки затем стал возвращать `relevant`. Второй ручной поиск не вызвал его: суммарно один вызов. Он только вернул старую строку inbox. - Где: [app.ts:1018–1032](apps/api/src/app.ts#L1018).
- Последствие: временный сбой модели/карточки становится постоянной ручной очередью; review в одном профиле мешает разбору в другом.
- Исправление: кэшировать по профилю, версии плана/алгоритма и возрасту данных; не кэшировать недоступность как окончательный результат; ручное «перепроверить» должно реально запускать разбор.

Снова `needs_human` → строка возвращается во входящие (в ручном поиске, включая отклонённую — discovery не дёргает её каждый проход); `relevant` → продвигается в очередь поиска; `irrelevant` → фиксируется отказ профиля. Опция `restoreReviewInbox` и счётчик `restoredReview` удалены. Регрессия: API-тест — `needs_human` → порт «выздоровел» → повторный поиск вызывает проверку и карточка попадает в очередь.

### [x] R07 · P1 · Решение зависит от порядка лотов, а не от наличия подходящего лота

**Воспроизведено.** Профиль НКУ для насосов, исключено освещение. Лоты `[«Поставка НКУ для освещения», «Поставка НКУ для насосов»]` дают `discard`, score 40; обратный порядок — `match`, score 100.

- Причина: выбирается первый `explicit` через `.find`, даже если у него `decision: discard` из-за назначения; более подходящий следующий лот не рассматривается.
- Исправление: оценивать лоты независимо, агрегировать по явной политике наличия подходящих лотов, возвращать их номера. Не смешивать предметы разных лотов.
- Приёмка: перестановка лотов не меняет результат; подходящий лот не скрывается неподходящим первым.

**Исправлено (этап 67).** `scoreIntentProcedure` больше не берёт первый `explicit`: лоты оцениваются независимо, клаузы ранжируются по решению (`match` > `review` > `veto` > `discard`) и оценке; подходящий лот побеждает сомнительного или неподходящего соседа. Каждый лот остаётся отдельным предметом — доказательства разных лотов не склеиваются. В причину добавлен номер лота (`Лот N: …`). `REVIEW_ALGORITHM_VERSION` поднят до `search-review-v5`, чтобы автоматические вердикты старого алгоритма пересматривались; ручные решения сохраняются.
