# STAGE-100 · Отмена поиска и независимые профили (R35)

## Проблема

Пока шёл поиск, отключались и кнопка, и select профиля: долгий прогон
профиля A не давал работать с профилем B. Отмены не было вовсе, а
listing-фаза показывала искусственно растущие до 90% проценты вместо
честного состояния.

## Решение

**Сервер.**

- `SpecialistSearchRunStatus` += `cancelled` — терминальный статус,
  иммутабелен: поздние `scored`/`skip`/`finish` из ещё разматывающегося
  цикла не могут вернуть «scoring» или «done» (заодно закрыт старый люк,
  когда `scored` после `done` оживлял ран).
- `SearchProgressHub.cancel(profileId)`:
  - живой ран → статус `cancelled`, `isCurrent` становится false →
    `runAlive()` в `scorePendingHits` обрывает цикл на ближайшей
    проверке — оставшиеся карточки не оцениваются;
  - рана ещё нет (listing в полёте) → маркер `cancelledAhead` (TTL 60 с):
    когда listing завершится и `begin` доложит ран, он ложится уже
    отменённым и цикл выходит на первой итерации. Маркер сгорает после
    потребления или по TTL — случайный cancel не отравляет следующий
    поиск.
- `POST /api/procurements/search/cancel {profileId}` — отменяет ран
  указанного профиля, отвечает снапшотом рана; зеркалируется в
  `workspace.searchRuns`, как и остальные мутации прогресса.
- Уже оценённые карточки сохранены: `persistEach` пишет каждый матч по
  мере оценки, отмена только прекращает дальнейшую работу.

**Веб.**

- Select профиля не отключается во время прогона — прогресс привязан к
  `runId`/профилю рана, переключение просто меняет видимую очередь.
- Кнопка «Остановить» рядом с «Искать по профилю» пока `listing ||
  scoring`; цель — `searchRun.profileId` (ран сам знает свой профиль), а
  не текущий выбор в селекте.
- Отмена listing-фазы: `searchGeneration` инвалидирует поздний ответ
  `search()` — результат и busy-флаг не воскрешают отменённый запрос.
- Прогресс: убран фейковый рост до 90% — listing показывает
  indeterminate-полосу (один платформенный вызов — честно считать нечего),
  реальные проценты начинаются со scoring (`scoredCount/retrievedCount`).
- Нотис `cancelled`: «Поиск по профилю «…» остановлен — уже найденные
  карточки остались в списке»; после отмены список профиля перечитывается
  с сервера.

## Регрессии

- `search-progress.test.ts` (3): cancel живого рана → `isCurrent` false,
  поздние записи no-op; cancel до `begin` → ран ложится cancelled; новый
  `begin` после отмены работает нормально;
- `app.test.ts`: `stops the remaining scoring on cancel and keeps what
  it already found` — первая карточка оценена и в очереди, вторая после
  cancel не оценивается, статус `cancelled`;
- `ProcurementsApp.test.tsx` (2): select активен во время scoring,
  «Остановить» зовёт `cancelSearch` с профилем рана; нотис для
  `cancelled` и отсутствие кнопки после остановки.
