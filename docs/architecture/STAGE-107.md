# STAGE-107 · Актуальная спецификация: состояние поиска, очереди, совместимость (R44)

Дата: 2026-05-06. Статус: выполнено.

Единый источник истины по тому, какие данные переживают повторный поиск и
рестарт, и какие версии клиента/сервера совместимы. Исторические этапы
(STAGE-63/64/66 и ранее) описывают своё время; при расхождении верен этот
документ и код.

## 1. Состояние поиска по профилю

На профиль хранятся **независимо** от других профилей:

- `searchIdsByProfile[profileId]` — очередь карточек текущего поиска
  (вкладка «Закупки» этого профиля);
- `searchRuns[profileId]` — последний прогон: `runId`, `status`
  (`retrieving|scoring|done|cancelled|interrupted`), счётчики.

Записи:

- ручной поиск с `offset = 0` → `replaceSearchIds(profile.id, [])` — очередь
  **этого** профиля заменяется; чужие очереди не трогаются;
- match по мере оценки → `appendSearchId`; решение по карточке
  («Участвовать»/«Отслеживать»/«Не нужно») → `removeSearchId` во всех
  очередях;
- слежение профиля докладывает новые id в его очередь;
- отмена → статус `cancelled` терминальный; уже найденные карточки остаются
  в очереди (R35, STAGE-100);
- рестарт во время прогона → сохранённый ран помечается `interrupted`,
  очередь и найденные карточки читаются из хранилища (R16, STAGE-88).

## 2. Что пишется в SQL/JSON (`isPersistableCabinetCase`)

В кабинет persist'ятся:

1. решённые карточки (`triage` задан) — участвую/слежу/не нужно;
2. review-кандидаты (`foundAs === "review"`);
3. карточки, входящие в `searchIdsByProfile` хотя бы одного профиля.

Не хранятся: строки площадки, не вошедшие ни в одну очередь и не получившие
решения, — plus undecided-карточки старше `caseMaxAgeMs` вычищает prune
(вне очередей и без решения).

Слепая проекция списка никогда не затирает полную карточку (STAGE-96/101).

## 3. Совместимость контрактов

Правила:

- **Опциональные добавленные поля** (`SpecialistSearchResponse.run`, поля
  прогресса, `lastSuccessAt`) — обратно-совместимы: старые клиенты их
  игнорируют.
- **Новые значения enum** — односторонняя совместимость. Новые данные под
  новой схемой читаются; **старая схема новые значения отвергает**. Пример:
  `ChangeKind.procedure_candidate` (STAGE-63) — откат сервера ниже этой
  версии с новыми inbox-строками ломает парсинг входящих.
- **Ослабление литерала** (`urgent: literal(true) → boolean`) — безопасно
  для читателей старых данных; старый клиент, ждавший `true`, получит и
  `false` — UI уже умеет (STAGE-98).
- **Новые эндпоинты** (`/api/live`, `/api/health` v2, `/cancel`) — аддитивны;
  отсутствие на старом сервере = фича недоступна, не поломка.

Вывод для деплоя: обновление сервера вперёд безопасно при старых данных;
откат безопасен только если в данных не появлялись enum-значения, которых
старая схема не знает. `GET /api/health` отдаёт `sha` деплоя (R42) — по нему
проверяется, какая схема актуальна.

## 4. Проверка (acceptance-тесты, подтверждающие спецификацию)

- замена очереди при новом поиске и независимость профилей —
  `apps/api/src/app.test.ts`, `SpecialistApp.storage.test.tsx`;
- очередь и ран переживают рестарт, `interrupted` — persist/search-run
  тесты (R16, STAGE-88);
- `cancelled` терминальный — R35 регрессии (STAGE-100);
- слияние проекций не затирает карточку — STAGE-96/101 тесты.
