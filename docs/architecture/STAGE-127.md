# Этап 127 — модель называет направление отказов, код проверяет каждую фразу

## Цель

Терм-сигнал этапа 122 находит повторяющееся слово/фразу в отказах. Но
специалист может отклонять разные по словам закупки одного направления:
«закрытие ЦТП-10», «реконструкция ИТП», «тепловые сети квартала» — общего
терма нет, сигнал молчит, а направление есть. Понять «это одна тема» может
только семантика, поэтому группировку делает модель — но исключение в
профиль она не пишет: каждую фразу проверяет код.

## Решение

`offerSuggestion` (app.ts) не нашёл терм-сигнал → fire-and-forget
`offerDirectionSuggestion`: «Не нужно» никогда не ждёт модель.

Пороги запуска: ≥3 взятых (как у терм-сигнала) и ≥6 отказов в первый раз;
повторный анализ — только после ещё 3 новых отказов
(`directionAnalyzedAt` помнит счётчик на момент последнего прогона, чтобы
тихий профиль не платил за модель).

Модели (`AssistantDirectionPort`, OpenAI-совместимый `chat/completions`,
тот же `LLM_API_KEY`; `ASSISTANT_DIRECTIONS=off` выключает) уходят
название профиля, слова поиска и исключения, до 40 предметов отклонённых
и до 40 взятых закупок. Она группирует отказы в направления и возвращает
для каждого `name` + `phrases` — подстроки, которыми эти закупки названы
в предметах.

Прежде чем проверять, каждая фраза проходит `reusableDirectionPhrase`:
хвост с идентификатором конкретного объекта — «№432», название в
кавычках — обрезается, потому что исключение по имени объекта прячет
один объект, а не направление. «Реконструкция ВЛ 330 кВ №432 «ГРЭС-20 –
Мирадино»» превращается в «Реконструкция ВЛ 330 кВ» и проверяется как
обычная фраза; фраза, состоящая только из идентификатора, умирает.

`validateAssistantDirections` (domain) отбрасывает фразу, если она:

- ловит меньше двух разных отклонённых предметов;
- встречается хоть в одном взятом предмете;
- целиком покрыта словами поиска профиля;
- пересекается по стемам с существующим исключением или с уже
  предлагавшимся термом (dedupe по `termKey`-стемам).

Направление выживает, только если его фразы суммарно объясняют ≥2 отказов.
Перед показом повторно проверяется «одно открытое на профиль»: пока модель
думала, терм-сигнал мог уже открыть предложение.

Записи памяти из хранилища приходят неупорядоченными; перед срезом в 40
предметов они сортируются по `decidedAt`, чтобы модель видела свежие
решения профиля, а не самые старые (проявлялось бы при >40 решениях).

Предложение несёт `label` — читаемое имя направления («тепловые пункты») —
и новое поле `phrases` (миграция 0016, колонка jsonb default `[]`).
«Принять» пишет в `excludeKeywords` все выжившие фразы; у старых записей
с пустым `phrases` — как раньше `label`. Карточка перечисляет, что именно
добавится в исключения.

## Почему так

- Модель только называет: любой её ответ проходит валидацию по той же
  памяти решений, что породила сигнал. Галлюцинированная фраза не ловит
  двух отказов — и умирает в коде, не долетев до интерфейса.
- Порог «≥2 предмета на фразу» отсекает направление из одного примера и
  одновременно требует, чтобы фраза была реальной подстрокой предметов,
  а не пересказом.
- `phrases` отделено от `label`: имя читается человеком, исключения
  пишутся конкретными фразами — «ЦТП», «ИТП», «тепловые сети» — а не
  свободным названием направления.

## Регрессии

directions.test.ts: фраза ловит ≥2 отказов и ни одного взятого; фраза во
взятых отброшена; фраза без поддержки отброшена; фраза, покрытая словами
профиля/исключением/прошлым предложением, отброшена; направление из
одного предмета не предлагается; примеры — заголовки покрытых отказов.

decision-memory.test.ts: API-путь — порт вернул направление → предложение
с `phrases` во входящих, «Принять» пишет все фразы в `excludeKeywords`;
невалидный ответ модели → тишина; открытое предложение блокирует второе.

db.integration.test.ts: `phrases` переживает запись и чтение хранилища.
