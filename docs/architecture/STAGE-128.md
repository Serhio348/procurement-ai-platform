# Этап 128 — второй источник: БУТБ за флагом и пилотом по кабинетам

## Цель

Добавить zakupki.butb.by вторым источником закупок так, чтобы активные
специалисты не почувствовали ни одной ошибки адаптера: код приезжает
выключенным, включается сначала на одном кабинете, откатывается флагом
без чистки данных.

## Что за сайт

БУТБ — JSF/ICEfaces-приложение с серверным состоянием сессии (разведка
этапа: живой прогон через сервер). Прямых URL на карточки нет — карточка
существует только «внутри сессии»: постбек по id ссылки строки реестра
возвращает 302 на `/auctions/viewinvitation.html`. Реестр ~230 тыс.
записей, 20 на страницу, свежие сверху.

Серверная форма поиска реестра **используется** — это единственный
способ достать закупки, чей предмет есть в карточке, но не в наименовании
(живой замер: скан 600 свежих строк дал 0 настоящих попаданий — все совпадения
были «КРУ»/«НКУ»/«ТП» подстрокой в чужих словах, а «подстанция» прячется
в «Закупка электротехнического оборудования для объектов капстроительства»).
Цена вопроса — известная деградация: при развёртывании панели поиска и на
каждом «Искать» таблица в сессии схлопывается до одной колонки «Вид
закупки». Лечится постбеком «Сохранить» меню «Столбцы» со всеми 11
чекбоксами — таблица возвращается в 12 колонок (плюс «Регион
заказчика/организатора»), фильтр при этом сохраняется. Полная цепочка
проверена живьём: expand → «Подстанция» → total=413 → restore →
pageChange по отфильтрованной выдаче.

Тот же принцип «retrieval отдельно, оценка потом»: адаптер забирает
кандидатов нативным поиском по «Предмет закупки», дальше платформа
решает релевантность сама. Форма поиска ломается → fallback на старый
скан реестра с локальным title-фильтром (уже, но честно).

Два факта протокола, найденные живым смоуком на проде и важные для
понимания кода:

- **GET реестра не сбрасывает таблицу**: сервер держит «текущую страницу»
  в сессии и на повторный GET `reestrauctions.html` отвечает ею же —
  после глубокого скана «страница 1» приходила с строками страницы 12.
  Поэтому навигация возможна только `pageChange`-постбеками, а реальную
  страницу клиент определяет из абсолютных индексов строк в linkId
  (`fra:reestrAu:{index}:_t*`, `detectRegistryPage`), а не из того, что
  запрашивал.
- **Сессия одноразовая для карточки**: возврат в реестр после карточки
  (GET на registry URL) отдаёт ту же деградированную таблицу — одна
  колонка, без пагинатора, linkId `…:_t346` вместо `…:_t344`. Состояние
  не чинится на том же jsessionid, поэтому после открытой карточки
  клиент делает полный `#resetSession` (куки включительно) и занимает
  новую сессию — дешевле, чем охота за способом «откатить» view.

## Состав адаптера

`mcp/procurement/src/butb-parser.ts` — разметка: строки реестра
(`fra:reestrAu_row_*` + ссылка `fra:reestrAu:{index}:_t*`), partial-response
XML (`<update id="fra:reestrAu"><![CDATA[…]]>`), карточка (label→value,
лоты, документы `/auctions/download?…`), ViewState/ice.window/ice.view.
id ссылок берутся из разметки, поля карточки — по подписям, а не по
сгенерированным id компонентов: перенумерация `j_idt*` сайт переживёт.
Поисковая форма разбирается тем же принципом: `butbSearchToggleId` ищет
ссылку по тексту «Раскрыть/Закрыть форму поиска» и вынимает id из её
`form['fra:j_idcl'].value`, `parseButbSearchForm` находит поля по
подписям (`<span>` перед `input.iceInpTxt`, `label[for]` у чекбоксов) —
«Предмет закупки», рег. номер, заказчик/УНП, группа «Состояние»
(«подача предложений / документов» → значение `2`), чекбоксы «Столбцы»
и id «Сохранить». Валидаторы `butbSearchApplied` (баннер «Критерии
поиска:») и `butbTableUsable` (≥10 заголовков vs 1 при деградации)
отличают «искренне применено» от «разметка не та». Строка реестра
бывает двух форм: 11 ячеек (обычная) и 12 (после restore — колонка
«Регион» сдвигает индексы на 1; `buyerRegion` читается только там).

`mcp/procurement/src/butb-http.ts` — сессионный транспорт: cookie jar,
захват/эхо ViewState, pageChange-постбеки, постбек карточки по linkId,
отслеживание реальной страницы таблицы и текущего view (реестр/карточка),
`ButbViewExpiredError` → полный сброс сессии (куки тоже) и один повтор.
`filteredPage(criteria, page)` гоняет нативный поиск: при смене критериев —
expand (один раз на сессию) → «Искать» с предметом/статусами/номером/
заказчиком → «Сохранить» колонок; при тех же критериях — голый
pageChange по отфильтрованной модели. Чекбоксы уходят повторными полями
`name=value` (`Record<string, string | string[]>`). Сессия умерла между
страницами → guarded-retry перепрогоняет всю цепочку на новом view.
`clearSearch()` сбрасывает сессию, чтобы забытый фильтр не отравил
следующий locate/скан; обычный `registryPage` после поиска сам берёт
чистую сессию — поисковая сессия «грязная» по определению.
Троттлинг
(`BUTB_BY_RATE_LIMIT_RPM`, умолчание 12/мин — ниже goszakupki: протокол
тяжелее), таймаут, лимит размера ответа, circuit breaker (3 сбоя →
пауза 30 c), сериализация запросов и FIFO-мьютекс операций:
`withSession(fn)` держит сессию на последовательность «найти строку →
открыть карточку» — linkId существует только пока таблица показывает его
страницу.

`mcp/procurement/src/butb-source.ts` — `ProcurementSourcePort`:
`sourceProcurementId = "butb/" + рег.номер` (`butb/AU20261015396707` —
регистрационный номер и есть стабильный публичный идентификатор; дата
публикации зашита в сам номер). `search` идёт нативно: для каждого терма
профиля — свой submit «Предмет закупки» (поле принимает одну строку),
`statuses`/номер/заказчик/УНП едут в той же форме, дальше pageChange по
filtered-модели до `totalRecords` или page-cap; наборы мерджатся и
дедупятся по рег.номеру (термы кандидата накапливаются в
`matchedSearchTerms`). Остальные фильтры запроса — локальные, как в
скане. Fallback: нет `filteredPage` у клиента или форма бросила —
warn + старый скан реестра с локальным title-фильтром; `clearSearch` в
`finally` не даёт поисковому состоянию протечь в скан или locate.
Курсор нативного окна — не якорь строки: merged-выдача отсортирована
поперёк термов, поэтому токен хранит `{m:"n", ret: сколько кандидатов
уже отдано}` и resume перечитывает всё окно, пропуская отданный префикс
(повторно отданные строки дедупит вызывающий). Курсор скана нативному
поиску не подходит и наоборот — каждый путь принимает только свой режим,
чужой токен = честный warn + проход с начала. `publishedFrom` — водяная
метка (строки по убыванию даты), page-cap `maxSearchPages`, wall-clock
`maxSearchMs` и `hasMore` ведут себя как у goszakupki. `get` находит
строку по номеру: кэш последней известной позиции `registryNumber →
абсолютный индекс` (сеется из поиска и удачных locate, лимит 10k) →
старт с хинт-страницы, дальше экспоненциальный прыжок 2,4,8… по дате
публикации из номера + бинарный поиск границы; одинаковая дата
публикации может занимать несколько страниц — страт даты дочитывается
целиком, а не до первой строки «другой» даты. Карточка кешируется на
60 с (несколько вызовов get/getLots/getStatus по кейсу не дёргают
сайт). `download` — только свой origin, чужие ссылки уходят в общий
`downloadPublicDocumentation`.

## Изоляция — почему прод не заметит

0. **Граница процессов** (найдено живым смоуком): `mcpChildEnv` пропускает
   в дочерний MCP-процесс только whitelisted env — `BUTB_ENABLED` /
   `BUTB_TLS_INSECURE` точечно и `BUTB_BY_*` префиксом. Без этого источник
   регистрируется на бумаге (API-флаг) и падает «not configured» внутри
   ребёнка. `/api/health` теперь честный: `procurement.sources` пробует
   реальный реестр ребёнка — `components.sources` = факт,
   `sourcesConfigured` = намерение API, расхождение → `degraded`.
   Плюс скан ограничен стеночасами (`BUTB_BY_MAX_SEARCH_MS`, 90 с <
   таймаут инструмента 120 с) — без водяной метки 30 страниц при
   12 rpm не успевали и возвращали пустую страницу.
1. `BUTB_ENABLED` (выкл. по умолчанию) — источник не регистрируется в
   реестре MCP: кода нет в маршрутах.
2. `BUTB_WORKSPACE_IDS` — фан-аут поиска добавляет `butb` только
   кабинетам пилота (тот же предикат, что `ASSISTANT_WORKSPACE_IDS`;
   `*` — всем). Гейт читает `app.currentWorkspaceId()` — экспортированный
   ALS-текущий кабинет.
3. Фан-аут (`createProcurementSearchHits`): каждый источник вызывается
   независимо, падение одного = пустая страница от него + warn, а не
   исключение. Мердж по дате публикации, `hasMore` — OR.
4. `card-watch` маршрутизирует `read`/`probeDocument` по префиксу id
   (`butb/…`) и по хосту документа — один проход слежения обслуживает
   обе площадки без разделения линий.
5. Данные не смешиваются: `butb/…` id'шки не пересекаются с
   `auction/…`/`request/…` goszakupki. Откат = флаг выкл + рестарт.
6. Health: `components.sources` перечисляет включённые источники.

## Ограничения пилота (честно)

- Одна и та же закупка может существовать на обеих площадках (у БУТБ
  есть «Номер закупки в ГИАС»). Кросс-источниковая дедупликация по ГИАС
  пока не сделана — хиты придут парами, карточки разные. Следующий этап.
- `search` — нативный поиск по «Предмет закупки» с fallback на скан
  реестра. Цена нативного пути — ~2 постбека на терм (submit + restore
  колонок) плюс pageChange на 20 строк выдачи: при 20 термах и 12 rpm
  прогон занимает минуты, бюджеты `maxSearchPages`/`maxSearchMs` и
  курсор `ret` держат его честным при усечении. Диапазоны дат и фильтры
  «вид процедуры/товар» формы пока не прокинуты — статусы, номер и
  заказчик уже нативные.
- История событий карточки БУТБ в fixture отсутствовала — `history`
  пуст; дифф-слежение подхватит изменения полей карточки, но не
  «События» как на goszakupki.

## Порядок выката

1. Деплой с `BUTB_ENABLED` пустым → прод идентичен прежнему.
2. `BUTB_ENABLED=1` + `BUTB_WORKSPACE_IDS=<админ-кабинет>` → рестарт →
   поиск/слежение БУТБ только у пилота.
3. Наблюдение журнала/health → `*` всем или доработка.
