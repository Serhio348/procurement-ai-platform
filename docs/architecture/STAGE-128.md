# Этап 128 — второй источник: БУТБ за флагом и пилотом по кабинетам

## Цель

Добавить zakupki.butb.by вторым источником закупок так, чтобы активные
специалисты не почувствовали ни одной ошибки адаптера: код приезжает
выключенным, включается сначала на одном кабинете, откатывается флагом
без чистки данных.

## Что за сайт

БУТБ — JSF/ICEfaces-приложение с серверным состоянием сессии (разведка
этапа: живой прогон через сервер). Прямых URL на карточки нет — карточка
существует только «внутри сессии»: постбек по id ссылки строки реестра
возвращает 302 на `/auctions/viewinvitation.html`. Реестр ~230 тыс.
записей, 20 на страницу, свежие сверху.

Серверная форма поиска реестра не используется: при её развёртывании
таблица в сессии деградирует до одной колонки «Вид закупки» до конца
сессии (проверено живьём). Поэтому адаптер идёт по страницам реестра
новизной и фильтрует термы профиля локально — то же «retrieval отдельно,
оценка потом», только retrieval здесь скан, а не выдача по слову.

## Состав адаптера

`mcp/procurement/src/butb-parser.ts` — разметка: строки реестра
(`fra:reestrAu_row_*` + ссылка `fra:reestrAu:{index}:_t*`), partial-response
XML (`<update id="fra:reestrAu"><![CDATA[…]]>`), карточка (label→value,
лоты, документы `/auctions/download?…`), ViewState/ice.window/ice.view.
id ссылок берутся из разметки, поля карточки — по подписям, а не по
сгенерированным id компонентов: перенумерация `j_idt*` сайт переживёт.

`mcp/procurement/src/butb-http.ts` — сессионный транспорт: cookie jar,
захват/эхо ViewState, pageChange-постбеки, постбек карточки по linkId,
`ButbViewExpiredError` → переоткрытие сессии и один повтор. Троттлинг
(`BUTB_BY_RATE_LIMIT_RPM`, умолчание 12/мин — ниже goszakupki: протокол
тяжелее), таймаут, лимит размера ответа, circuit breaker (3 сбоя →
пауза 30 c), сериализация запросов и FIFO-мьютекс операций:
`withSession(fn)` держит сессию на последовательность «найти строку →
открыть карточку» — linkId существует только пока таблица показывает его
страницу.

`mcp/procurement/src/butb-source.ts` — `ProcurementSourcePort`:
`sourceProcurementId = "butb/" + рег.номер` (`butb/AU20261015396707` —
регистрационный номер и есть стабильный публичный идентификатор; дата
публикации зашита в сам номер). `search` сканирует страницы реестра,
`publishedFrom` — водяная метка ранней остановки (строки по убыванию
даты: страница целиком старше метки → глубже смысла нет), page-cap
`maxSearchPages` и `hasMore` ведут себя как у goszakupki. `get` находит
строку по номеру: быстрый путь — первая страница, дальше экспоненциальный
прыжок 2,4,8… по дате публикации из номера + бинарный поиск границы;
карточка кешируется на 60 с (несколько вызовов get/getLots/getStatus по
кейсу не дёргают сайт). `download` — только свой origin, чужие ссылки
уходят в общий `downloadPublicDocumentation`.

## Изоляция — почему прод не заметит

1. `BUTB_ENABLED` (выкл. по умолчанию) — источник не регистрируется в
   реестре MCP: кода нет в маршрутах.
2. `BUTB_WORKSPACE_IDS` — фан-аут поиска добавляет `butb` только
   кабинетам пилота (тот же предикат, что `ASSISTANT_WORKSPACE_IDS`;
   `*` — всем). Гейт читает `app.currentWorkspaceId()` — экспортированный
   ALS-текущий кабинет.
3. Фан-аут (`createProcurementSearchHits`): каждый источник вызывается
   независимо, падение одного = пустая страница от него + warn, а не
   исключение. Мердж по дате публикации, `hasMore` — OR.
4. `card-watch` маршрутизирует `read`/`probeDocument` по префиксу id
   (`butb/…`) и по хосту документа — один проход слежения обслуживает
   обе площадки без разделения линий.
5. Данные не смешиваются: `butb/…` id'шки не пересекаются с
   `auction/…`/`request/…` goszakupki. Откат = флаг выкл + рестарт.
6. Health: `components.sources` перечисляет включённые источники.

## Ограничения пилота (честно)

- Одна и та же закупка может существовать на обеих площадках (у БУТБ
  есть «Номер закупки в ГИАС»). Кросс-источниковая дедупликация по ГИАС
  пока не сделана — хиты придут парами, карточки разные. Следующий этап.
- `search` — локальный фильтр по заголовку; поля «Предмет закупки» у
  сервера нет в обходе, поэтому глубину закрывает водяная метка +
  page-cap: для discovery (свежее) этого хватает, для ретро-поиска —
  нет, там серверная форма с датами нужна отдельным этапом.
- История событий карточки БУТБ в fixture отсутствовала — `history`
  пуст; дифф-слежение подхватит изменения полей карточки, но не
  «События» как на goszakupki.

## Порядок выката

1. Деплой с `BUTB_ENABLED` пустым → прод идентичен прежнему.
2. `BUTB_ENABLED=1` + `BUTB_WORKSPACE_IDS=<админ-кабинет>` → рестарт →
   поиск/слежение БУТБ только у пилота.
3. Наблюдение журнала/health → `*` всем или доработка.
