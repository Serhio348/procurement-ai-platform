# Этап 131 — ручной поиск в «Закупки», discovery во «Входящие»

## Цель и проблема

Результаты ручного поиска должны появляться во вкладке «Закупки».
Фоновое слежение за профилем должно приносить новые закупки во «Входящие»,
где специалист выбирает «Открыть карточку», «Не нужно» или «Удалить».
Изменения в отслеживаемых закупках также поступают во «Входящие».

Раньше общий обработчик оценки всегда вызывал `appendSearchId` для match.
Discovery дополнительно создавал inbox-событие: новая закупка попадала
сразу в оба раздела. Сомнительные результаты ручного поиска, наоборот,
отправлялись во входящие. Ещё один путь утечки был в клиенте: ответ
`resolve(action=dismiss)` содержал карточку, которую UI безусловно
добавлял в локальный список закупок.

## Решение и поведение

| Источник или действие | Результат |
|---|---|
| Ручной поиск, match | Очередь «Закупки» выбранного профиля |
| Ручной поиск, review | Та же очередь, пометка «Требует проверки» |
| Ручной поиск, irrelevant | Отсев |
| Discovery, новая match/review | Только «Входящие» |
| Изменение отслеживаемой закупки | «Входящие», прежний механизм мониторинга |
| «Открыть карточку» нового кандидата | Закрытие входящей записи, очередь профиля происхождения и карточка |
| «Не нужно» | Решение reject, корзина, снятие входящих и поисковых очередей |
| «Удалить» | Снятие уведомления, без добавления карточки в «Закупки» |
| Повтор discovery после разбора | Та же находка повторно не объявляется |
| Явный ручной поиск после удаления уведомления | Закупка может появиться в ручном поиске; отказ reject/hide остаётся сильнее поиска |

Режим определяется источником запуска. Асинхронная проверка карточек,
запущенная кнопкой поиска, остаётся частью ручного поиска.
Счётчики match не включают review, хотя обе категории доступны в списке.
Фоновый отсев по другому профилю не удаляет карточку, удерживаемую оценкой
первого профиля и его входящими.

## Хранение и совместимость

Нельзя просто убрать `appendSearchId`: без очереди match раньше не
сохранялся и удалялся при prune. `retainedCabinetCaseIds` собирает ID
из поисковых очередей **и всех записей inbox**, включая снятые.
Этот набор используется в полном/точечном persist и в prune.
Снятая запись сохраняет идентичность уже известной находки и не превращается
в новую после рестарта. Inbox-stub без сохранённой карточки сам по себе
не становится кейсом.

При первом открытии кабинета старые queue-ID, одновременно присутствующие
в открытых событиях `new_found`/`review`, снимаются с поисковых очередей.
Карточки, события и решения сохраняются. Данные, у которых входящее
уведомление уже было закрыто, автоматически не перераспределяются:
старое состояние не позволяет достоверно отличить ручное открытие от
старого ошибочного добавления discovery.

Схема БД и формы API/MCP не меняются. Изменена маршрутизация результатов
и содержимое существующего ответа ручного поиска: `items` включает review,
`relevantCount` по-прежнему считает только match.

## Изменения

- `apps/api/src/app.ts`: маршрутизация, счётчики, сохранность другой
  профильной оценки, исправление старого пересечения очередей при открытии.
- `apps/api/src/cabinets.ts`, `persist.ts`: общий набор удерживаемых кейсов.
- `apps/web/src/SpecialistApp.tsx`: dismiss не запоминает возвращённую карточку.
- `ProcurementsApp.tsx`, `RelevanceNote.tsx`: подписи проверки ручных результатов.
- Существующие API, persistence, UI и e2e тесты приведены к этим правилам.
- `STAGE-107.md` обновлён как актуальная спецификация очередей.

## Проверка и критерии приёмки

- API-регрессии проверяют разделение ручного поиска/discovery, все три
  действия inbox, отсутствие повторного объявления и сохранность ручной очереди.
- Отдельная регрессия проверяет восстановление старого пересечения
  очереди и inbox без удаления данных.
- Persistence-тест на файлах и PostgreSQL проверяет открытый и снятый
  match после рестарта, prune и повторного discovery.
- UI-регрессия: «Удалить» → переход в «Закупки» не показывает удалённую находку.
- E2E ручного поиска открывает review прямо в «Закупках» и проверяет
  сохранение решения после reload.

Обязательная проверка: `npm run verify` с отдельной `TEST_DATABASE_URL`.
Рабочая база не используется для тестовых записей.
