# Этап 133 — Админ удаляет пользователя и кабинет

## Цель

До этого админ мог только одобрять/отклонять/отзывать доступ и менять роль.
Удалить ошибочную заявку, тестовый аккаунт или весь кабинет специалиста
было нельзя — данные копились.

## Решение

**`AuthDirectory.remove(id)`** — единая точка удаления аккаунта
(directory.ts + memory + postgres):

- возвращает удалённую запись для журнала;
- сессии и password-reset'ы уходят вместе с пользователем (Postgres —
  каскадами `auth_sessions`/`auth_password_resets`, memory — явной чисткой);
- last-admin guard: удаление *активного* админа проверяет, что останется
  другой активный админ, иначе `AuthConflictError("last_admin")`. Проверка
  срабатывает только для активного админа — pending/specialist удаляются
  всегда, даже до появления первого админа;
- Postgres-версия — в транзакции с `SELECT ... FOR UPDATE` по `auth_users`:
  та же дисциплина, что у `replaceStatus`, чтобы удаление не гонялось с
  понижением роли последнего админа (R39).

**Кабинет.** `CabinetRegistry.deleteWorkspace(workspaceId)` +
`specialist-store.deleteWorkspace`:

- под `withRlsBypass` дети удаляются явно, в порядке зависимостей:
  procurement_profiles → inbox → decisions → review_verdicts →
  decision_memory → assistant_suggestions → telegram_sent →
  procurements → settings → profiles → members → сам workspace.
  Явный порядок обязателен: каскад, сработавший после удаления родителя,
  упирается в RLS-политику ребёнка и откатывает всё (та же ловушка, что в
  `removeCases`);
- канонические `procurements`/`documents` — общий каталог, не трогаются:
  удаляется только принадлежность кабинета;
- `persist.ts`: вытеснение из кэша до и после стирания (кабинет, открытый
  в полёте, не должен продолжать жить), чистка `deletedProfileIds`,
  удаление файлов-зеркал `${id}.json`/`${id}.cases.json`/
  `${id}.inbox.json`, чтобы удалённый кабинет не воскрес через файловый
  fallback;
- `TEST_WORKSPACE_ID` — общий тестовый/legacy-кабинет, стирание отклонено
  (`false`) ещё до очереди записей.

**Роуты.**

- `DELETE /api/admin/users/:id` (register.ts): self-delete →
  `409 cannot_delete_self`; перед удалением аккаунта вызывается
  `purgeUserWorkspace` — membership, по которому находится личный
  workspace, каскадно умирает вместе с user, поэтому кабинет стирается
  заранее; ошибка purge пишется в журнал, но не блокирует удаление
  аккаунта; успех — запись `«… удалил пользователя: …»`.
- `DELETE /api/admin/cabinets/:workspaceId` (app.ts): workspaceId ищется
  среди кабинетов пользователей из `listAdminCabinets`; нет такого → 404;
  успех возвращает обновлённый список кабинетов и пишет `«… удалил
  кабинет: …»`.
- Оба роута под общим admin-гейтом `onRequest` (`mayAdministerUsers`) —
  отдельной проверки роли в хендлерах нет, как у approve/reject/revoke.

**UI.**

- `AdminApp.tsx`: кнопка «Удалить» у каждого пользователя, кроме текущего
  (self-delete запрещён и на бэке); confirm с явным «безвозвратно».
- `CabinetsPane.tsx`: «Удалить» в строке кабинета и «Удалить кабинет» в
  карточке; confirm объясняет, что у пользователя останется пустой кабинет;
  при удалении открытого кабинета — переход на список.
- `api/auth.ts`: `deleteUser`, `deleteAdminCabinet` — 409/404 мапятся в
  понятные русские ошибки.

## Что не изменилось

- Удаление пользователя не удаляет канонический каталог закупок и
  документы в MinIO — они общие для всех кабинетов.
- «Отозвать доступ» (revoke) остаётся мягким сценарием: аккаунт и данные
  живы, вход закрыт. «Удалить» — необратим.
- Кабинет можно удалить и у живого пользователя: при следующем запросе
  `ensurePersonalWorkspace` создаст пустой — это и есть «сбросить кабинет».

## Регрессии

- `memory-directory.test.ts`: удаление с сессиями и reset-токенами,
  last-admin, pending без админа.
- `register.test.ts`: удаление юзера — сессия мертва, кабинет стёрт,
  журнал записан; self-delete 409; specialist → 403; wipe кабинета →
  workspaceId пропадает из списка, повтор → 404.
- `postgres-directory.integration.test.ts` (TEST_DATABASE_URL): каскады
  сессий/сбросов, last_admin — в CI.

## Продовые заметки

- Удаление кабинета — тяжёлая операция (десятки таблиц под RLS bypass);
  на больших кабинетах выполняется в одной транзакции — при необходимости
  позже можно вынести в фон.
- Журнал хранит имя/email удалённого — аудит-след сохраняется после
  удаления аккаунта.
