# Этап 28 — журнал обслуживания в админке

**Статус:** вкладка «Администрирование» показывает ленту событий.
Красная метка «ошибки N» в меню — число ошибок за 7 дней. Сырой
`journalctl` в браузер не выводим.

---

## 1. Цель

Администратор видит, кто менял доступ и что сломалось у площадки, без SSH.

---

## 2. Архитектурное решение

```text
действие / сбой
  → recordJournal (append-only)
  → PostgreSQL admin_journal  или память процесса
GET /api/admin/journal
  → последние 200 строк + errorCount (7 дней)
GET /api/auth/session  (admin)
  → errorEventCount → метка «ошибки N»
```

Пишем только:

- доступ: заявка, одобрение, отказ, смена роли, отзыв;
- вход и выход: кто вошёл; сколько был в системе по `lastSeenAt`
  (не до нажатия «Выйти» — закрытая вкладка считается по последнему запросу);
- новый вход закрывает старые сессии того же человека и пишет длительность;
- ошибки: поиск, слежение, документы, PostgreSQL/Redis;
- неудачный пароль в журнал не пишем.

Успешные поиски и «Участвовать» в ленту не кладём.

---

## 3. Почему именно так

**Не хвост логгера.** Структурный JSON остаётся в systemd. В консоли —
короткие русские строки.

**Счётчик по окну, не за всю историю.** Иначе через месяц «ошибки 400».

**Append-only.** Строки журнала нельзя править и удалять из API.

---

## 4. Изменения БД

Таблица `admin_journal`, миграция `0003_admin_journal.sql`.
Колонка `auth_sessions.last_seen_at`, миграция `0004_session_last_seen.sql`.

---

## 5. Контракты API

- `GET /api/admin/journal` — admin;
- `AuthSessionUser.errorEventCount` — только admin.

---

## 6. Критерии приёмки

- [x] одобрение пользователя появляется в журнале;
- [x] вход и выход сотрудника видны в фильтре «Доступ», с длительностью;
- [x] недоступная площадка увеличивает errorCount;
- [x] меню показывает «ошибки N»;
- [x] тесты без живой площадки.
