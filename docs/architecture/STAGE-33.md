# Этап 33. Жизненный цикл карточки: найдена, взята, решена, убрана

## Цель

Список «Закупки» не должен превращаться в склад. До этого этапа каждый поиск
писал все найденные карточки, включая сомнительные, в `specialist_cases`, и
`GET /api/procurements` отдавал всё накопленное за месяцы. Специалист видел
«СО2-инкубатор» рядом с реальными подстанциями и не мог понять, откуда он.

## Решение: не кеш, а состояние в БД

Рассматривался вариант держать результаты поиска в Redis и писать в
PostgreSQL только при «Следить/Участвовать». Отклонён: Входящие ссылаются на
карточку по `procurementId`, фоновое слежение должно доносить находки до
специалиста через сутки, дедупликация между профилями держится на одной
карточке. Кеш с TTL порвал бы эти связи. Вместо этого карточка получила
признаки жизненного цикла и уборку внутри каталога.

### Контракт (`packages/contracts/src/specialist.ts`)

`SpecialistProcurementCard` дополнен:

- `foundAs: "match" | "review"` — как карточка попала в консоль. `match` —
  уверенное совпадение по ключевым словам. `review` — слабое (слово внутри
  чужого кода) или без совпадений; ждёт во Входящих и не показывается в
  списке, пока специалист её не откроет или не примет решение.
- `lastSeenAt` — когда поиск в последний раз вернул эту процедуру.

Оба поля необязательны, старые карточки в БД парсятся без миграции.

### Домен

`search-cards.ts`: `cardFromRelevantHit` ставит `foundAs: "match"`,
`cardFromWeakHit` и `cardFromAmbiguousHit` — `"review"`.

`SpecialistCatalog.prune({ now, maxAgeMs, keepSourceIds })` удаляет
недорешённые live-карточки, которые поиск не возвращал дольше `maxAgeMs`.
Legacy-карточка без `lastSeenAt` считается устаревшей — так уходит мусор,
накопленный до этого этапа. Карточки из fixture-inbox (`live: false`) не
трогаются. Строки Входящих для убранных карточек гасятся, чтобы Входящие не
указывали на несуществующую карточку. `procurements()` больше не
восстанавливает убранную карточку из истории Входящих.

### API (`apps/api/src/app.ts`)

- `rememberFound(card, profileId, now)` — единая точка записи найденной
  карточки для ручного поиска и фонового слежения. Существующая карточка
  сохраняет документы и факты; обновляются только заголовок, статус, сумма,
  `lastSeenAt` и привязка к профилю. `review` повышается до `match`, если
  новый поиск дал точное совпадение; обратного понижения нет. Раньше ручной
  поиск перезаписывал карточку целиком и мог потерять скачанные документы.
- `listed()` скрывает `foundAs === "review"` без решения.
- `pruneStaleCases()` вызывается после каждого ручного поиска и каждого
  прохода слежения; убранные id уходят в `removeCases`.
- «Открыть карточку» из Входящих (`/api/inbox/:id/resolve`, любое действие
  кроме `dismiss`) переводит `review` в `match` — специалист взял её в работу.
- Новые опции `buildSpecialistApi`: `removeCases`, `caseMaxAgeMs`
  (по умолчанию 7 дней, `DEFAULT_CASE_MAX_AGE_MS`).

### БД (`packages/db/src/specialist-store.ts`, `apps/api/src/persist.ts`)

`removeCases(ids)` удаляет строки `specialist_cases`. Нормализованные
`procurements` остаются как история: там нет мусора для специалиста, а
`decisions` и `change_events` на них ссылаются.

## Состояния карточки

```
поиск → review ──(открыл из Входящих / точное совпадение)──→ match
           │                                                   │
           │  (Следить / Участвовать / Не нужно)               │
           └──────────────→ decided ←──────────────────────────┘

review, match без решения и без lastSeenAt за 7 дней → убрана
decided — не убирается никогда
```

## Тесты

- `catalog.test.ts`: `prune` убирает устаревшую и legacy-карточку вместе со
  строкой Входящих, оставляет свежую и решённую.
- `app.test.ts`: review-карточки не в списке, но во Входящих; «Открыть»
  переводит в список; через 8 дней без результатов нерешённые уходят из
  каталога, Входящих и БД (`removeCases` вызван с 3 id); решённая карточка
  переживает месяц без поиска.

`npm run verify` — зелёный.

## Что даёт специалисту

- После обновления при первом же поиске старые карточки без `lastSeenAt`
  уйдут сами. Отдельная SQL-чистка больше не нужна.
- В «Закупках» — только уверенные совпадения и то, что специалист взял или
  решил. Сомнительное — во Входящих, откуда его можно открыть или удалить.

## Риски

- Семь дней — константа в коде. Если специалист ищет реже, уверенные
  совпадения, которые он не успел посмотреть, исчезнут. Вынести в настройку
  профиля можно, когда появится запрос.
- Уборка идёт по `lastSeenAt` активного поиска. Карточка, найденная одним
  профилем и не встречающаяся в поисках другого, живёт по общему таймеру, а не
  по профилю — при нескольких активных профилях это ожидаемо, потому что
  слежение проходит по всем.
