# Этап 34. Разбор сомнительных находок: карточка, потом модель

## Цель

После этапа 32 сомнительные находки перестали попадать в список, но их разбор
целиком лёг на специалиста. Каждый поиск оставлял во Входящих десятки строк
вида «СО2-инкубатор» или «Реконструкция ВЛ-0,4 кВ от БКТПБ-746», по которым
консоль не сказала ничего, кроме «точных совпадений по словам нет».

Задача этапа — чтобы платформа сама доводила такую находку до вердикта: сначала
дешёвой проверкой по карточке площадки, и только для оставшихся неясных — через
модель. Специалисту должно доставаться то, что действительно требует человека.

## Решение: два шага, оба под контролем кода

```
слабая находка
  → procurement.get (карточка, лоты, описание, ОКРБ, rawFields)
  → тот же матчер терминов, что и по заголовку
      точное совпадение в лоте → relevant   (модель не вызывается)
      исключённое слово        → irrelevant (модель не вызывается)
      всё ещё неясно           → модель
  → вердикт модели + порог уверенности в коде
      relevant/irrelevant выше порога → принимается
      ниже порога, битый ответ, сбой   → needs_human
```

Почему так:

- **Карточка дешевле модели.** Заголовок на площадке часто безличный
  («Поставка оборудования»), а нужное слово стоит в названии лота. Это решается
  без LLM, и это же объясняет, откуда взялась находка.
- **Исключения сильнее модели.** Проверка по карточке идёт до вызова модели,
  поэтому исключённое слово в лоте закрывает вопрос, и модель просто не может
  его переголосовать.
- **Вердикт не равен уверенности.** Модель возвращает `verdict` и
  `confidence`, но принимает решение код: `relevant` ниже порога профиля
  становится `needs_human`. Модель по-прежнему не ставит оценку 0–100.
- **Сбой не значит «подходит».** Недоступная карточка, недоступная модель,
  ответ не по схеме, исчерпанный лимит вызовов — всё это `needs_human` с
  причиной, а не молчаливое принятие или молчаливое удаление.

### Домен (`packages/domain/src/search/review.ts`, новый)

Чистая логика без HTTP и MCP:

- `cardReviewText(card)` — текст, в котором ключевое слово имеет право стоять:
  заголовок, названия и описания лотов, ОКРБ, позиции, `rawFields`.
- `reviewByCard(card, profile)` — прогон `cheapClassifyHit` по этому тексту.
  Слово точно в лоте равноценно слову точно в заголовке.
- `outcomeFromCardReview(result)` — `relevant` / `irrelevant` или `undefined`,
  если карточка не решила вопрос.
- `buildSearchClassifierInput(profile, hit, card)` — вход модели: профиль
  (имя, назначение, инструкции, ключевые и исключённые слова), находка и
  урезанная карточка (до 8 названий лотов, до 12 полей `rawFields`).
- `outcomeFromModel(raw, minConfidence)` — разбор ответа модели и применение
  порога.
- `quotaOutcome()`, `unavailableOutcome()` — безопасные исходы, когда модели
  нет или лимит вызовов исчерпан.

`ReviewOutcome.decidedBy` (`card` | `model` | `quota` | `none`) попадает в
шаги карточки, чтобы специалист видел, кто именно вынес вердикт.

### API (`apps/api/src/search-review.ts`, `search-classifier.ts`, новые)

`createProcurementSearchReview` — порт разбора для консоли:

- карточка берётся через `ProcurementMcpClient` с `ToolPolicyGate`, где
  разрешён только `procurement.get`;
- `maxModelCalls` (по умолчанию 50) ограничивает расход модели на один поиск,
  `concurrency` (по умолчанию 4) — параллельные проверки;
- `minConfidence` (по умолчанию 0.7) совпадает с `minConfidenceToDecide`
  профиля электрооборудования.

`createOpenAiCompatibleSearchClassifier` — HTTP-оболочка DeepSeek на стороне
API. Дублирование с `apps/agent-runtime` сделано осознанно: правило слоёв
запрещает `apps/api` импортировать agent-runtime, а общей осталась именно
логика вердикта — она живёт в `packages/domain`. `createSearchClassifierFromEnv`
читает `LLM_API_KEY`, `LLM_BASE_URL`, `LLM_MODEL`, `LLM_TIMEOUT_MS`; без ключа
порт работает без модели и отдаёт неясные находки человеку.

### API (`apps/api/src/app.ts`)

- Новая опция `buildSpecialistApi`: `searchReview`. Её отсутствие — рабочий
  режим: всё сомнительное ждёт во Входящих, как на этапе 33.
- `reviewAmbiguous(...)` — общий путь для ручного поиска и фонового слежения:
  `relevant` повышается до `foundAs: "match"` и попадает в список, `irrelevant`
  уходит в `discardedCount` и не создаёт строку Входящих, остальное остаётся
  review-карточкой с причиной в шагах.
- Отклонённые специалистом процедуры не отправляются на разбор повторно.

### `selectRelevantSearchCards`

Добавлено `ambiguousHits` — исходные строки выдачи в том же порядке, что
`ambiguousCards`. Без них API не мог бы обратиться к `procurement.get`:
`SpecialistProcurementCard` не хранит `sourceId`.

### `main.ts`

Порт разбора создаётся только в live-режиме, когда есть MCP. Модель
подключается, если задан `LLM_API_KEY`; факт подключения пишется в лог
(`Search review configured`).

## БД и контракты

Изменений схемы нет. `SpecialistProcurementCard`, `SearchClassifierInput` и
`DomainSearchCandidate` используются как есть — вердикт модели разбирается той
же схемой, что у `DomainSearchAgent`.

## Тесты

`packages/domain/src/search/review.test.ts`:

- слово точно в названии лота принимает находку с безличным заголовком;
- исключённое слово в описании лота отбрасывает её;
- повтор чужого кода (`БКТПБ-746`) карточку не решает — вопрос идёт дальше;
- неуверенный `relevant` и битый ответ (`{ score: 87 }`) становятся
  `needs_human`;
- вход модели содержит текст профиля и не больше 8 лотов.

`apps/api/src/search-review.test.ts`:

- карточка решает вопрос без вызова модели;
- исключение в карточке срабатывает раньше модели, даже если модель сказала
  бы «подходит»;
- модель вызывается только для неясной карточки и получает лоты;
- уверенность 0.55 при пороге 0.7 → `needs_human`;
- недоступная карточка вместе с упавшей моделью → `needs_human`, не принятие;
- без классификатора все неясные находки уходят человеку;
- `maxModelCalls: 2` на трёх находках даёт два вызова и один `quota`.

`apps/api/src/app.test.ts`:

- ручной поиск: проверенная находка попадает в список как `match` с причиной в
  шагах, явно неподходящая исчезает совсем, неясная остаётся во Входящих;
- фоновое слежение проходит тот же разбор, и `addedCount` считает только
  принятые.

`npm run verify` — зелёный (378 тестов, 306 модулей без нарушений слоёв).

## Риски

- **Расход модели.** Один поиск может дать до 50 вызовов. Лимит — константа
  порта, не настройка профиля. Если специалист ищет по широким словам, часть
  находок вернётся с `quota`, а не с вердиктом; это видно в причине.
- **Задержка ручного поиска.** На каждую сомнительную находку добавляется
  `procurement.get`, при неясной карточке — ещё вызов модели.
  Параллелизм 4 сглаживает это, но поиск по широкому профилю станет заметно
  дольше. Переносить разбор в фоновую очередь стоит, когда это начнёт мешать.
- **Дубль HTTP-клиента модели.** Оболочка DeepSeek теперь в двух местах.
  Слить их можно только вынеся LLM-транспорт в отдельный пакет; до появления
  третьего потребителя это преждевременно.
- **Порог 0.7 — константа порта.** Профиль хранит `minConfidenceToDecide`
  только в БД-таблице `domain_profiles`, а рабочий профиль консоли
  (`SpecialistWorkingProfile`) его не имеет. Пока они совпадают по значению;
  связать их следует, когда рабочий профиль получит настройки порогов.

## Критерии приёмки

- Находка, у которой ключевое слово стоит в лоте, попадает в «Закупки» с
  указанием, что решение принято по карточке.
- «СО2-инкубатор» при ключевом слове `НКУ` не попадает ни в список, ни во
  Входящие.
- Ни один сбой (площадка, модель, схема, лимит) не приводит к появлению
  закупки в списке без человека.
- Без `LLM_API_KEY` консоль работает как на этапе 33.
