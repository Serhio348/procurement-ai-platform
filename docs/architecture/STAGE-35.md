# Этап 35. Слежение за новыми: водяной знак, живучесть, память

## Цель

Разбор фонового слежения (после этапа 34) показал четыре пробела, из-за
которых «Следить за новыми закупками» видело меньше, чем обещало, и тратило
больше, чем нужно:

1. Фоновый проход брал 20 самых свежих строк. Адаптер площадки перебирает
   ключевые слова по очереди и выходит, набрав лимит, поэтому при широком
   первом слове остальные слова в проходе не запрашивались вовсе.
2. Проход не помнил, что уже смотрел. Каждый час — те же строки, тот же
   `procurement.get`, тот же вызов модели по тому же инкубатору.
3. Сбой поиска по одному профилю бросал исключение из цикла: остальные
   профили в этот час не проверялись, найденное не сохранялось.
4. Строки Входящих жили только в памяти. После перезапуска API review-карточки
   оставались в БД скрытыми от списка, а строка, через которую их можно было
   открыть, исчезала — и не создавалась заново, потому что карточка уже
   известна.

Этот этап закрывает все четыре. Он же — фундамент для этапа 36 (мониторинг
карточек с решением): событие «цена изменилась» нельзя терять из-за рестарта.

## Решения

### Водяной знак вместо лимита

`SpecialistWorkingProfile.lastDiscoveryAt` — когда фоновый проход по профилю
в последний раз **начался**. Следующий проход передаёт площадке
`created_from = lastDiscoveryAt − 1 сутки` (`discoveryPublishedFrom` в
`workspace.ts`). Площадка возвращает только свежее; лимит перестаёт быть
потолком, а число запросов к площадке падает, а не растёт.

Почему начало прохода, а не конец: процедура, опубликованная пока проход шёл,
должна попасть в следующее окно, а не потеряться между ними.

Почему сутки запаса: площадка фильтрует по календарной дате, часовые пояса и
задним числом выложенные извещения иначе выпадут.

Знак живёт на профиле, сбрасывается при смене ключевых или исключённых слов
(новые слова требуют полного прохода) и **не** отдаётся в `SpecialistProfileWrite`:
форма профиля не может его ни затереть, ни подделать. Ручной поиск знак не
использует — специалист, нажавший «Найти», хочет всё.

Лимит фонового прохода поднят с 20 до 100 (`DEFAULT_DISCOVERY_LIMIT`). С водяным
знаком это потолок для первого прохода и для очень плотного дня, а не часовая
квота.

### Память о вердиктах модели

`SpecialistWorkspaceState.reviewedIrrelevant` — список `{profileId,
sourceProcurementId, decidedAt}` для находок, которые разбор (карточка или
модель) уверенно назвал неподходящими. Это **не решение специалиста**:
хранится отдельно от `decisions`, не влияет на список и на «Отклонить».

`reviewAmbiguous` в `app.ts` теперь пропускает:

- находки, уже запомненные как неподходящие для этого профиля — считаются
  `discardedCount`, модель не вызывается;
- находки, уже лежащие во Входящих как review-карточки — обновляется
  `lastSeenAt`, считаются `ambiguousCount`, повторного разбора нет.

Вердикт привязан к профилю: инкубатор не подходит под «электрооборудование»,
но может подойти под «лабораторное оборудование». Память стирается при смене
слов профиля и по возрасту (30 дней, `REVIEW_VERDICT_MAX_AGE_MS`), а также для
удалённых профилей.

### Один профиль не роняет проход

Цикл по профилям в `runDiscovery` ловит ошибку поиска, пишет её в журнал с
именем профиля (`discoveryFailedMessage`) и идёт дальше. Успешные профили
получают водяной знак; уборка и `persist()` выполняются. Итоговая запись
«Фоновый поиск выполнен» перечисляет только успешные профили. Исключение из
`runDiscovery` летит наружу только если **все** профили упали — тогда
эндпоинт по-прежнему отвечает 503/504, а BullMQ считает задание неудачным.

### Входящие в PostgreSQL

Таблица `specialist_inbox` (миграция `0005_specialist_inbox.sql`): `id` =
`change.id`, `procurement_id`, `item jsonb`, `detected_at`. Формат — тот же
`InboxFixtureItem`, что и в памяти, по образцу `specialist_cases`.

Почему не существующая `change_events`: у неё внешний ключ на `procurements`
и на документы, а строки Входящих консоли создаются раньше нормализованной
записи и не привязаны к версиям документов. Смешивать консольные строки с
будущими событиями мониторинга в одной таблице с чужими инвариантами — путь к
ошибкам вставки в самый неподходящий момент.

- `persist()` пишет все строки Входящих (включая погашенные) через
  `persistInbox`; погашение хранится в `dismissedInboxIds` на workspace, как и
  раньше.
- `hydrateCatalog` после карточек поднимает строки Входящих.
- `removeCases` удаляет строки Входящих вместе с карточкой.
- Если таблицы нет (миграция не применена), API падает при старте с явным
  сообщением, а не откатывается молча на диск: карточки уже подняты из
  PostgreSQL, и «частично из БД, частично с диска» хуже честной ошибки.

## Риски

- **`persist()` по-прежнему пишет всё.** Карточки и Входящие переписываются
  целиком после каждого поиска. Пока строк сотни — терпимо; это первое, что
  надо менять, когда мониторинг карточек начнёт добавлять события каждый час.
- **Память вердиктов — 30 дней и по профилю.** Процедура, ошибочно названная
  моделью «не подходит», не будет пересмотрена месяц, пока специалист не
  изменит слова профиля. Порог 0.7 и вызов модели только после карточки
  снижают вероятность, но не до нуля. Показывать запомненные вердикты в
  админке — отдельная работа.
- **Знак на календарную дату.** При интервале слежения меньше суток соседние
  проходы перекрываются почти полностью — это ожидаемо и дёшево, потому что
  повторы отсекаются памятью и известными карточками, а не сетью.
- **Rate-limit площадки не измерялся.** Число запросов с этим этапом падает,
  но что считает «слишком часто» сама goszakupki.by, мы не знаем.

## Критерии приёмки

- Второй и последующие фоновые проходы отправляют площадке `created_from`;
  после смены ключевых слов — не отправляют.
- Инкубатор проверяется моделью один раз за месяц, а не каждый час.
- Отказ площадки по одному профилю виден в журнале и не мешает другим.
- После перезапуска API review-карточки открываются из Входящих.
