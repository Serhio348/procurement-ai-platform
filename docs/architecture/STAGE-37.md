# Этап 37. Слежение за решёнными закупками

## Цель

Специалист нажал «Следить» или «Участвовать» — значит, за этой закупкой нужно
смотреть дальше, а не забывать. Задача этапа: на каждом фоновом проходе заново
читать карточку у источника и писать во входящие только **реальные** изменения.

Главный риск, который этап закрывает: **ложные тревоги**. На сайте цена может
быть напечатана «1 000,00 руб.» сегодня и «1 000.00 BYN» завтра — сумма та же,
а строка другая. Если сравнивать строки как есть, каждый проход будет кричать об
изменении, и входящие потеряют смысл.

Второй риск — **лишние запросы**. Карточка читается через `procurement.get` —
это дешевле, чем качать документы. Пока список файлов не изменился, файлы не
трогаем вообще.

## Решения

### 1. Снимок карточки — `CardWatchSnapshot`

`packages/domain/src/specialist/watch.ts` собирает из `ProcedureCard` снимок:
статус, дедлайн, цена (и печатная строка, и нормализованный ключ), список
документов как отсортированная строка, остальные поля. Снимок живёт на карточке
кейса — `SpecialistProcurementCard.watchSnapshot` — и сохраняется вместе с ней
в `specialist_cases`. После рестарта сервиса история сравнения не теряется.

### 2. Сравнение — `diffCardSnapshots`

Сравнивает два снимка и отдаёт список изменений:
`status_changed`, `deadline_changed`, `price_changed`, `documents_changed`,
`fields_changed`. Важные детали:

- цена сравнивается по `normalizePriceKey`: «1 234,56 руб.», «1 234.56 BYN» и
  «1.234.567,89» дают один ключ — ложных срабатываний по формату нет;
- пропавшее поле — не изменение: если страница просто перестала отдавать цену,
  тревоги не будет;
- список документов сравнивается отсортированным, поэтому перестановка файлов
  тревогу не вызывает.

### 3. Порт для чтения карточки — `card-watch.ts`

`apps/api/src/card-watch.ts` — адаптер, который через `procurement.get` в
Procurement MCP перечитывает карточку по `sourceProcurementId`. Ошибка источника
возвращает `undefined`, не роняя весь проход.

### 4. Мониторинг внутри `runDiscovery`

`apps/api/src/app.ts`:

- на каждом проходе, до поиска новых, обходятся карточки с решением
  `monitor`/`participate` и флагом `live`;
- порядок — `watchOrder`: ещё не читанные идут первыми, дальше — от самого
  старого снимка;
- лимит `SPECIALIST_WATCH_LIMIT` (по умолчанию 40) защищает от слишком длинного
  прохода;
- перед каждым `procurement.get` — `beforeRequest` контроллера, то есть
  слежение подчиняется тому же темпу и пробойнику, что и поиск;
- найденное изменение записывается во входящие тем же `catalog.record`, что и
  изменения из MonitoringAgent; карточка кейса сразу обновляется через
  `applyInboxChangeToCard`;
- снимок обновляется в любом случае: если изменений не было, следующее
  сравнение будет от свежей точки.

Ответ `SpecialistDiscoveryResponse` вырос на `monitoredCount` и `changedCount`;
в журнал администратора пишется итог проверки слежения.

## БД

Новых таблиц нет: снимок — часть `specialist_cases.data`. Это осознанный
выбор: снимка достаточно одного, последнего. Если понадобится история
значений (а не только событий), понадобится отдельная таблица.

## API

- `POST /api/profile/discovery` — в ответе `monitoredCount` и `changedCount`.
- Входящие получают темы `card_update` и `docs_changed` по обычным правилам.

`npm run verify` — зелёный.

## Риски

- **Содержимое документов не сравнивается.** `documents_changed` значит
  «изменился список файлов» — имя, ссылка, роль. Файл могли перезалить с тем же
  именем — мы это увидим только после скачивания, а качаем лишь когда список
  изменился.
- **Снимок один, последний.** Истории «цена была X, стала Y, потом Z» в
  карточке нет — есть события во входящих. Этого хватает для реакции, мало для
  аналитики тренда.
- **`SPECIALIST_WATCH_LIMIT` может задерживать проверку.** При большом числе
  отслеживаемых карточек часть переносится на следующий проход — это намеренно,
  но админ должен видеть очередь через `monitoredCount` и `watchedCount`.
- **Мониторинг только live-карточек.** Кейсы, пришедшие из inbox без живого
  `sourceProcurementId`, не перечитываются.

## Критерии приёмки

- Решённая «Следить»/«Участвовать» закупка перечитывается на каждом фоновом
  проходе и в ручном `POST /api/profile/discovery`.
- Перепечатка цены другим форматом не создаёт события.
- Смена статуса, срока или списка документов создаёт одну запись во входящих,
  карточка обновляется, снимок сохраняется между перезапусками.
- Мониторинг подчиняется замку, темпу и пробойнику Этапа 36.
- `npm run verify` проходит.
