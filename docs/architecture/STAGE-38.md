# Этап 38 — карточка площадки при «Участвовать»

## Цель

Вкладка «Мои закупки» должна показывать ту же таблицу, что специалист видит
на goszakupki.by: заказчик (имя, адрес, УНП, контакты), даты, стоимость,
плата оператору, требования, иные сведения. Сейчас после «Участвовать»
консоль рисовала тонкий снимок поиска (имя и сумма из списка) и не читала
страницу источника.

## Решение: снять карточку в момент решения, дальше читать из кейса

```
«Участвовать» / «Следить»
  → procurement.get          # полная ProcedureCard
  → сохранить в sourceCard
  → «Участвовать» дополнительно качает документы, как этап 24
«Мои закупки»
  → рисует stored.sourceCard, без повторного запроса
фоновый проход
  → тот же procurement.get обновляет sourceCard и watchSnapshot
```

Почему не грузить карточку при каждом открытии вкладки:

- «Участвовать» и так ходит на площадку за файлами; один `procurement.get`
  дешевле комплекта PDF и даёт поля, которые файлы не содержат.
- Повторный `get` на каждый клик умножает нагрузку на goszakupki.by и
  оставляет экран пустым, если источник в этот момент недоступен.
- Слежение этапа 37 уже перечитывает карточку; отображение должно жить на
  том же снимке, а не в отдельном live-запросе UI.

«Следить» получает тот же снимок без скачивания файлов: вкладка «Мои
закупки» общая, одно `procurement.get` не равно разбору ТЗ.

Если `procurement.get` не удался, решение всё равно записывается. На карточке
остаются данные поиска и кнопка «Обновить». `GET /api/procurements/:id/card`
при успехе тоже сохраняет `sourceCard` — для старых кейсов без поля.

## Парсер

Синонимы под вёрстку «закупающей организации» и ориентировочную стоимость.
`PlatformAmount.kind = indicative`, если на странице нет «предельной».
Оба числа, если они есть, остаются в `rawFields` и показываются как на сайте.

## UI

`ProcurementDetailApp` берёт `stored.sourceCard`. Поля площадки — сразу, не
в свёрнутом «Дополнительные сведения». Заголовок — AUC, не внутренний UUID.
Документы по-прежнему из кейса (после «Участвовать»).

## Файлы

- `packages/contracts/src/specialist.ts` — `sourceCard`
- `packages/domain/src/specialist/source-card.ts` — `applySourceCard`, строки таблицы
- `mcp/procurement/src/goszakupki-by-parser.ts` — синонимы и indicative
- `tests/fixtures/goszakupki-by/request-buying-org.html`
- `apps/api/src/app.ts` — гидратация при решении и при watch
- `apps/web/src/procurements/ProcurementDetailApp.tsx`

## БД

Нет миграции. `sourceCard` лежит в JSONB `specialist_cases.data`, как и
остальной кейс. Старые строки читаются без поля.

## Тесты

- парсер: УНП, адрес, контакты и 160 651.42 как `indicative`
- `applySourceCard` не затирает документы, подменяет сумму списка
- API: participate вызывает `procurement.get` до ingest
- UI: сохранённая карточка показывается без «Загрузка с площадки»

## Риски

- Лоты по-прежнему только из `#lotsList`. Если площадка рисует лоты скриптом,
  счётчик останется 0 — это ограничение адаптера, не вкладки.
- Снимок один, последний. История значений — во входящих, как на этапе 37.

## Критерии приёмки

- После «Участвовать» в «Мои закупки» видны УНП, адрес, контакты, даты и
  ориентировочная стоимость с карточки площадки.
- Повторное открытие вкладки не требует живого `procurement.get`.
- Документы по-прежнему качаются только при «Участвовать».
- `npm run verify` проходит.

## Исправление записи и повторного «Участвовать»

Persist валился целиком: уникальный `source_procurement_id`, NUL в jsonb со
страницы площадки, или сбой производных таблиц хешей. Скачивание ждало
`procurement.get` и вместе с ним не укладывалось в 180s nginx, поэтому
повторное «Участвовать» не доходило до файлов.

Теперь кейсы пишутся по одному, jsonb чистится от NUL, хеши не блокируют
карточку консоли, а `procurement.get` идёт **до** скачивания документов
(один stdio MCP нельзя дёргать параллельно). После решения UI обновляет
только эту карточку и не подменяет выдачу поиска всем каталогом из БД
(откуда и брались старые «Завершен»).
Журнал ошибок показывает причину PostgreSQL.
