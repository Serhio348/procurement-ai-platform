# Этап 44 — корзина «Не нужно» / «Убрать»

## Цель

«Не нужно» и «Убрать» больше не прячут закупку навсегда. Карточка уходит в
раздел **«Корзина»** главного меню: её можно открыть, вернуть в «Мои закупки»
или удалить окончательно.

## Архитектурное решение

`SpecialistTriageKind` не расширяется. «Не нужно» / «Убрать» по-прежнему пишут
`triage: "reject"` и оставляют источник в `rejectedSourceIds`, чтобы поиск и
discovery не предлагали процедуру снова.

Список корзины — раздел `/trash` и `GET /api/procurements?tab=trash`: строки
кабинета с `triage = reject`. Для этой вкладки API **не** передаёт
`rejectedSourceIds` в SQL, иначе корзина была бы всегда пустой.

```
Закупки ──«Не нужно»──▶ Корзина
Мои закупки / Архив ──«Убрать»──▶ Корзина
Корзина ──«Вернуть»──▶ Мои закупки (последнее Слежу/Участвую, иначе Слежу)
Корзина ──«Удалить»──▶ DELETE строки, решение reject остаётся
```

`POST /api/procurements/:id/restore` смотрит `lastWorkingKind`: последнее
`monitor` / `participate` в истории решений, иначе `monitor`. Документы заново
не качает. Архивный флаг снимается.

`DELETE /api/procurements/:id` только из корзины. `catalog.dropCase` помечает id
как pruned, затем `persistWorkspaceOnly`, затем `removeCases`. Дочерние строки
`workspace_procurement_profiles` удаляются **до** кейса: CASCADE + RLS, которая
смотрит на родителя, иначе PostgreSQL откатывает delete, API раньше отвечал 204
и карточка возвращалась после перезагрузки. Решение `reject` в workspace
остаётся — поиск молчит.

Список `?tab=trash` (и остальные вкладки) отдаёт плитки без документов и
extract: **SQL сам** возвращает `card` без `documents`, `extractPreview`,
`reportMarkdown` и `sourceCard.rawFields`, полная строка читается только по
`GET /:id`. После «Удалить» консоль не перечитывает вкладку. При PostgreSQL
`removeCases` не переписывает весь файловый дамп карточек.

Удаление не имеет права быть тихим. `removeCases` после DELETE проверяет, что
строк с этими id больше нет, и падает, если политика скрыла строку: иначе API
отвечал 204, а карточка возвращалась после перезагрузки. `catalog.upsertCase`
игнорирует id, уже помеченный `dropCase`, — иначе следующий `persist` в том же
процессе записывал удалённую карточку обратно.

## Почему так

Заказчик просил найти отложенную закупку, если она снова понадобится. Отдельный
вид triage «trash» дублировал бы `reject`. Архив — полка завершённых Слежу /
Участвую; корзина — отказ. Возврат в «Закупки» снова показывал бы карточку в
очереди поиска; возврат в «Мои закупки» совпадает с формулировкой заказчика.

## Контракты API

| Метод | Назначение |
|---|---|
| `GET /api/procurements?tab=trash` | страница корзины |
| `POST /api/procurements/:id/restore` | вернуть в «Мои закупки»; 400 `not_in_trash` |
| `DELETE /api/procurements/:id` | удалить из корзины; 204; 400 если не reject |
| `DELETE /api/procurements/trash` | очистить всю корзину кабинета; 204 |

Поиск по профилю по-прежнему пропускает `rejectedSourceIds`.

## Тесты

- domain: вкладка `trash` видна при `rejectedSourceIds`; `lastWorkingKind`;
  `dropCase` не собирает карточку из inbox-заглушки; persist пишет
  `storedCases`, не inbox-заглушки
- API: reject → `?tab=trash` → restore как participate → `?tab=all`; purge 204
  и поиск снова пуст; чужой кабинет и новый поисковый профиль не получают
  чужие reject
- web: раздел «Корзина» в меню, «Вернуть» / «Удалить» / «Очистить корзину»;
  карточка без Отслеживать; «Не нужно» / «Удалить» / очистка подтверждают toast

## Риски

- Окончательное удаление необратимо для карточки; источник всё ещё в reject,
  повторно из поиска не всплывёт.
- После purge inbox-строки этой закупки тоже снимаются (`removeCases`).
- Fallback без Postgres пишет JSON кабинета как раньше.
- Корзина — строки **этого** кабинета с `triage = reject`, не общая таблица
  отменённых. Новый специалист стартует с пустого кабинета. Новый поисковый
  профиль в том же кабинете делит ту же корзину.
- Persist больше не upsert'ит inbox-заглушки в `workspace_procurements`: после
  рестарта кабинета Postgres не поднимает все кейсы в память, и заглушки иначе
  создавали бы чужие/старые карточки заново.

## Дополнение R68 — возврат после массовой очистки

Воспроизведён отдельный дефект на реальном PostgreSQL: `listTrashIds` отдавал
`workspace_procurements.id`, а каталог и события используют `card.id` из JSON.
Эти UUID различаются: первый локален кабинету, второй сохраняет идентичность
карточки API. `dropCase` блокировал не тот ID; SQL DELETE проходил, но следующий
`persist` снова записывал оставшиеся в памяти карточки. В холодном кабинете тем
же несовпадением не закрывались загруженные inbox-строки.

Теперь `listTrashIds` выбирает `card->>'id'` без чтения полного JSON карточек.
`removeCases` уже умеет искать по этой идентичности. Массовое и одиночное
удаление также снимают ID со всех очередей поиска до сохранения workspace.
История решений `reject` остаётся, поэтому удалённая процедура не становится
новой после рестарта или поиска по другому профилю.

Связанный дефект поиска закрыт проверками решений перед review и после
асинхронных операций: поздний результат не возвращает удалённую карточку и не
объявляет `monitor`/`participate` новым кандидатом. См. дополнение R68 в
`STAGE-107.md`.

Проверки: `db.integration.test.ts` сравнивает ID корзины с ID API;
`persist.test.ts` выполняет DELETE через API на PostgreSQL, повторное сохранение,
переоткрытие persistence, ручной поиск и discovery. Покрыты четыре сочетания
(одиночное/массовое удаление × тёплый/холодный каталог), сохранность слежения и
независимость корзины другого кабинета с теми же source ID и card ID.

Контракты HTTP и схема БД не меняются. После `npm run build` и рестарта API
повторная очистка уберёт ранее вернувшиеся карточки; существующие данные не
удаляются автоматически. Несколько независимых процессов API с устаревшими
кэшами остаются ограничением STAGE-86: этот фикс не вводит распределённую
инвалидацию кабинетов.
