# Этап 48 — план поиска из фразы, оценка 0–100 считает код

## Цель

Поиск считал закупку подходящей, если в названии нашлось любое слово профиля.
«НКУ для управления насосами» находило монтаж, ремонт и обслуживание НКУ.
Специалист не должен писать основы слов. Модель не должна ставить балл.

## Архитектурное решение

```
профиль (название, слова, исключения)
  → SearchIntentPlan { objects, desired_actions, excluded_actions, intent }
      LLM (DeepSeek, JSON) или inferSearchIntentPlan, если ключа нет / ответ мусор
  → площадке уходят objects, не вся фраза
  → по каждой строке выдачи scoreSearchIntent (код)
      OBJECT_MATCH_WEIGHT / DESIRED_ACTION_WEIGHT / EXCLUDED_ACTION_PENALTY
  → match ≥ 55 в список, veto (предмет — монтаж/ремонт/…) отбрасывается,
     объект только в доп. тексте → не match
  → relevanceScore и relevanceReason пишет код
```

Модель заполняет только `SearchIntentPlan`. Поле `score` в её JSON выбрасывается
до Zod. Число 0–100 и фраза «почему» живут в `packages/domain/src/search/intent-score.ts`.

Veto осторожный: «поставка НКУ с последующим монтажом силами заказчика» —
упоминание, не предмет. «Выполнение работ по монтажу НКУ» — предмет, veto.

Заказчик (больница, завод) сам по себе не исключение: смотрим предмет закупки.

Без плана (`intent` не передан в `selectRelevantSearchCards`) поведение
прежнее: одно точное слово = match. Консоль всегда передаёт план.

## Почему именно так

Embeddings и векторный индекс на этом этапе не нужны: оси «объект / желаемое
действие / запрещённое действие» уже закрывают жалобу, их можно покрыть
юнит-тестами и объяснить специалисту одной фразой.

Нормализация (регистр, окончания, дефис) — в `query-terms.ts`, рядом с
прежним `term-match`. Короткие аббревиатуры по-прежнему не ищутся внутри
обычных слов («НКУ» в «банку»).

## Настройки

| Переменная | Смысл |
|---|---|
| `LLM_API_KEY` | без неё план строит `inferSearchIntentPlan` |
| `SEARCH_INTENT=off` | не звать модель, дешёвый план остаётся |
| `SEARCH_INTENT_MODEL` | иначе `LLM_MODEL` |
| `SEARCH_INTENT_TIMEOUT_MS` | таймаут разбора фразы |

## Тесты

- поставка НКУ → высокий score
- изготовление шкафа управления → высокий score
- монтаж / ремонт / пусконаладка НКУ → veto
- поставка НКУ с упоминанием монтажа силами заказчика → не veto
- НКУ только в дополнительном тексте → не match
- модель не может протащить `score` в план
- `SEARCH_INTENT=off`

## Риски

- Дешёвый план для профиля поставки добавляет исключения монтаж/ремонт/…
  даже если специалист их не вписывал. Профиль «пусконаладка» (слово в
  keywords) эти исключения не получает.
- Площадке уходят objects: запрос короче, строк больше, отбор строже. Если
  модель выкинет нужный объект, recall упадёт — тогда правится план, не score.
- Оценка 0–100 — про листинг, не итоговый балл закупки из `scoring/`.
