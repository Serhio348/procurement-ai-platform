# Этап 51 — фильтр выдачи, discard vs review, назначение в плане поиска

## Цель

Этап 50 показал, что веса object/action/veto не надо подгонять под dump.
Ломалась архитектура: площадка отдаёт «НКУ» внутри «конкурс», score 0 без
объекта шёл в review, «поставщика» считался поставкой, профиль «НКУ для
управления насосами» не требовал насосы.

## Архитектурное решение

```
профиль
  → SearchIntentPlan { objects, required_context, desired_actions,
                       excluded_actions, intent }
  → площадке по-прежнему уходят objects (НКУ, шкаф управления)
  → goszakupki.by: text=substring, ответ фильтруется listingMatchesAnyKeyword
     (termOccurs / exact для аббревиатур ≤3 букв)
  → scoreSearchIntent:
       объект нет            → discard (не review)
       required_context нет в тексте, чужое назначение явно → discard
       required_context нет в тексте, назначения нет       → review
       required_context совпал                             → плюс к score
       veto монтажа/ремонта без изменений
  → match / review / discard
```

Модель по-прежнему не ставит 0–100. Новые числа только на оси назначения:

| Вес | Значение | Зачем |
|---|---|---|
| `CONTEXT_MATCH_WEIGHT` | 15 | назначение найдено, как extra-text mention объекта |
| `CONTEXT_MISMATCH_PENALTY` | 50 | чужое назначение топит типичные 60, решение всё равно discard |
| OBJECT / DESIRED / EXCLUDED / MIN_MATCH | как на этапе 48 | **не** перенастраивались под F1 |

«Поставка НКУ 0,4 кВ» при профиле с насосами — review, не match.
«Шкаф управления освещением / котельной» — discard.
«Выбор поставщика …» не даёт desired «поставка»: основа «поставщик»
сохраняется до снятия «ка», иначе «поставщика» склеивалось с «поставка».

## Почему именно так

API goszakupki.by не даёт exact token. Режем шум после ответа, аббревиатуры
НКУ / КИП / МТР остаются целым токеном.

Пустая выдача «конкурсов» в review — не двусмысленность, а отсутствие объекта.
Review оставляем для пропуска назначения: «Поставка НКУ» может оказаться
насосной после документов.

## Риски

- `FOREIGN_PURPOSE` (освещение, котельная, котёл, теплосчётчик, вентилятор) —
  узкий лексикон при непустом `required_context`, не универсальный классификатор
  отраслей.
- Фильтр listing режет уже полученную страницу: площадка всё ещё качает
  «конкурсы» по substring, мы их выбрасываем.
- Review-порт (карточка / модель) видит только `review` скорера: пропуск
  назначения. Объект, который есть только в лотах, а в названии нет, больше
  не спасается вторым проходом.
- `evaluate:search` идёт через собранный `@procurement/contracts`. После
  смены схемы нужен `npm run build` / `typecheck`, иначе Zod срежет
  `required_context`.

## Критерии приёмки

- [x] listing «НКУ» не считает конкурс / инкубатор / Янкувер
- [x] score 0 без объекта → discard, не review
- [x] поставщик ≠ поставка
- [x] `required_context` в плане; пропуск назначения → review, чужое → discard
- [x] веса object/action/veto не трогали
- [x] `npm run evaluate:search` и `npm run verify`
