# Этап 59 — поиск: план параллельно со списком, разбор карточек в фоне

**Статус:** кнопка «Поиск» больше не ждёт DeepSeek и `procurement.get`.
Список площадки уходит сразу по дешёвому плану; модель дополняет фразы,
если добавила объекты. Сомнительные сразу во входящих, карточки
дочитывает фон кабинета.

Этапы 56–58 (лимит фраз, меньше страниц, «монтаж» из имени профиля)
откатили: они резали полноту и точность. Этот этап ускоряет тот же
поиск, не меняя веса 0–100 и не урезая выдачу площадки.

---

## 1. Цель

Живой поиск по профилю занимал минуту и больше: план модели → по фразе
несколько страниц с 20 req/min → до 50 `procurement.get` на сомнительные.
Специалист смотрел на крутилку, хотя оценки listing-score уже были.

Нужно быстрее нажать «Поиск» и увидеть совпадения, не теряя фразы,
страницы и Precision/Recall.

## 2. Архитектурное решение

```
кнопка «Поиск» и слежение профиля
  → fetchProfileHits
       inferSearchIntentPlan ∥ resolveSearchPlan
       procurement.search (дешёвые objects)
       extraPlatformSearchTerms → второй search только новых objects
       publishedFrom: пусто у кнопки, водяной знак у cron
  → selectRelevantSearchCards (веса STAGE-48/51)

«Поиск»:
  match → ответ HTTP
  review → inbox сразу (undismiss) + startListingReviewJob
       relevant → foundAs match
       irrelevant → forgetCase + rememberIrrelevant
       needs_human → review во входящих

слежение (watchNewProcurements):
  match → inbox только если карточки ещё не было
  review → reviewAmbiguous до persist (не фон)
  уже match → не переразбирать
  решённые (Участвовать / Слежу / Не нужно) → skip
  «Отслеживать»/«Участвовать»: monitorDecidedCases как раньше
```

Модель по-прежнему не ставит 0–100. `pagesPerTerm` и лимит фраз не
трогаем. Имя профиля не становится поисковой фразой площадки.

## 3. Почему именно так

План модели — JSON с объектами и типом закупки, не ranking. Пока он
идёт, площадке уже можно отдать НКУ из keywords. Если модель добавит
«шкаф управления», второй `procurement.search` догоняет, а не заменяет
первый.

`procurement.get` на сомнительные не должен блокировать кнопку: совпадения
listing-score специалисту уже полезны. Входящие заполняются сразу — счётчик
«сомнительных во входящих N» совпадает с `GET /api/inbox`. Повторный поиск
не зовёт модель, если карточка уже `foundAs: review`; снятую строку
`undismiss` возвращает.

`dropCase` (вечный `#pruned`) для промаха разбора нельзя: id карточки
стабилен от `sourceProcurementId`. Смена слов профиля должна уметь найти
ту же процедуру снова.

Слежение профиля — тот же listing, иначе cron находил бы меньше, чем кнопка.
Разбор в проходе остаётся синхронным: persist кабинета должен увидеть
вердикт. Уже принятый match не отправляем в `procurement.get` — иначе
ночной проход мог бы пометить его irrelevant. Снятую inbox-строку cron
не поднимает: это не новый запрос специалиста.

## 6. Контракты

`POST /api/procurements/search` тот же `SpecialistSearchResponse`.
`items` — только listing-score match. `ambiguousCount` — сколько строк
уже лежат во входящих (включая повторно найденные). После фона список
«Закупки» может пополниться promoted match без нового HTTP поиска.

## 7. Тесты

- listing стартует, пока план модели ещё не вернулся
- новый object модели даёт второй `procurement.search` и у кнопки, и у слежения
- ответ поиска не ждёт review; inbox сразу; фон promote / drop
- повторный поиск не зовёт review для уже `foundAs: review`
- слежение не переразбирает уже принятый match
- смена keywords снова спрашивает забытый irrelevant
- снятая inbox-строка возвращается при следующем поиске, не при cron
- `forgetCase` позволяет upsert того же id; `dropCase` — нет

## 8. Риски

- Фон после disconnect не показывается, пока специалист не обновит
  входящие / список. Консоль уже делает `refreshInbox` после поиска.
- Рестарт API посреди job теряет незаконченный разбор — как ingest.
- Два persist подряд (HTTP, затем job) на одном кабинете без очереди:
  тот же компромисс, что этап 52.
- Если модель добавит много новых objects, второй поиск всё ещё упирается
  в 20 req/min. Это полнота, не регресс точности.
