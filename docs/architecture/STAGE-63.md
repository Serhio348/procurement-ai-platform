# Этап 63 — план поиска виден и не сужается моделью, услуги не маскируются под поставку, кандидат ≠ новая закупка

## Цель

Устранить три причины ложной картины в консоли, видимой на живых данных:

1. профиль закупки оборудования показывал услуги и работы как «поставку»;
2. профиль работ показывал постороннее оборудование во входящих как «Новая закупка (срочно)»;
3. при массовых отказах не было видно, по какому плану искал поиск.

## Архитектурное решение

### 1. План модели может расширять детерминированный план, но не сужать его

`mergeSearchIntentPlans(inferred, fromModel)` в `intent-plan.ts`:

- `objects`, `desired_actions`, `excluded_actions`, `excluded_context` — объединение множеств, дедупликация;
- `required_context` берётся у модели, если она его назвала (дешёвый парсер читает только «для …»);
- `intent: "works"` детерминированного плана модель перебить не может;
- исключённое действие, совпадающее с желаемым действием профиля работ, выкидывается из `excluded_actions` — иначе профиль работ ветоил бы сам себя.

Раньше ответ модели **заменял** план целиком: `excluded_actions: []` от DeepSeek снимало veto на «обслуживание», «ремонт», «монтаж» — отсюда услуги в профиле поставки.

### 2. Услуга/работа в голове заголовка — предмет, а не упоминание

`SERVICE_HEAD` в `intent-score.ts`: если ведущая клауза заголовка начинается с носителя услуги/работ («услуги», «инжиниринговые услуги», «обслуживание», «эксплуатация», «выполнение работ», «работы») и желаемого действия в заголовке нет — для профиля поставки это `veto` с ролью `subject`, независимо от того, какое оборудование названо дальше.

Это закрывает дыру неявной поставки: «Инжиниринговые услуги (… модернизация сетей электроснабжения)» больше не получает +20 за «объект есть, действия нет → значит поставка». «Поставка КТП с услугами шефмонтажа» по-прежнему match — носитель не в голове.

Причина в `workLabel` переведена на человеческие метки: «услуги», «работы», «обслуживание», «эксплуатация».

### 3. Resolved-план логируется

`resolveSearchPlan` в `app.ts` пишет `Specialist search plan`: имя профиля, источник (`inferred` / `model+inferred`), все массивы плана и отдельно `modelOnly` — что именно добавила модель. Диагностика «почему отброшено 90 из 91» теперь начинается с чтения плана, а не с догадок.

### 4. Кандидат на проверку — не «новая закупка (срочно)»

Новый `ChangeKind.procedure_candidate` и новый `SpecialistInboxTopic.review`:

- `inboxItemFromFoundCard` для карточки `foundAs: "review"` пишет `kind: "procedure_candidate"`, `urgent: false`;
- `urgentInbox()` включает кандидатов наряду со срочными — разбор входящих не меняется;
- summary кандидата: «На проверку: — → <название>», без «(срочно)»; бейдж топика — «На проверку»;
- `SpecialistInboxEntry.urgent` ослаблен с `literal(true)` до `boolean` — срочность теперь данные, а не инвариант выборки;
- «Открыть карточку» на кандидате по-прежнему поднимает его в `match` (существующая семантика resolve).

Котёл из жалобы останется во входящих, но под меткой «На проверку» — видно, что это кандидат от широкого терма, а не подтверждённое совпадение.

## БД и контракты

Миграций нет. `InboxFixtureItem` с новым `kind` парсится старой схемой после деплоя; старые записи валидны. `SpecialistInboxEntry.urgent: boolean` — обратно-совместимо для читателей.

## Тесты

- сервисные заголовки («Инжиниринговые услуги…», «Техническое обслуживание…», «Услуги по эксплуатации…», «Выполнение работ…») → veto для профиля «КТП»; «Поставка КТП с услугами шефмонтажа» → match;
- модель не снимает `excluded_actions`/`objects` детерминированного плана и не превращает works-профиль в purchase;
- works-профиль: «Котёл твердотопливный» → discard;
- кандидат в inbox: `kind = procedure_candidate`, `urgent = false`, топик «На проверку», summary без «(срочно)».

## Проверка

- `npm run verify` — 578 + 74 теста, типы, линт, depcruise;
- `npm run evaluate:search` — новая выдача P/R/F1 100%, FP 0, FN 0 (старая — P 27.3%).

## Риски

- Больше candidates в inbox без «срочно» — осознанно: честная метка важнее ложной тревоги.
- `SERVICE_HEAD` ловит только носителя в голове ведущей клаузы; «… оказание услуг по обслуживанию» в середине заголовка решается существующими `excluded_actions`.
- Если модель вернёт объект-мусор, он добавится в objects — наблюдаемо через `modelOnly` в логе.

## Приёмка

- Профиль поставки не выдаёт услуги/работы как «поставку».
- Входящие различают «Новая закупка» (match) и «На проверку» (candidate).
- `journalctl -u procurement-api | grep "search plan"` показывает источник и содержимое плана каждого поиска.
