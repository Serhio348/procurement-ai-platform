# Этап 64 — listing это retrieval, оценка после карточки, список растёт по мере score

> **Исторический документ.** Актуальная спецификация — в [STAGE-107](STAGE-107.md).
> Раздел 2 ниже исправлен: с STAGE-66/R16 очередь поиска персистится в SQL —
> фраза «неиспользованные находки не пишутся» описывала промежуточное
> состояние и сегодня неверна.

**Статус:** строка списка площадки больше не пишет вердикт. Совпадение
считается после `procurement.get` (название + предмет лота). Каждая
подходящая карточка сразу попадает в SQL-список профиля; вкладка
«Закупки» не очищается при перезагрузке и смене раздела.

---

## 1. Цель

goszakupki.by ищет по «Заказчик и предмет закупки», но в HTML списка это
заголовок ссылки, а не `lots[].title`. Предмет лота есть только на
`/view/{id}`. Listing-score по title отбрасывал то, что площадка нашла
по лоту, и искусственный лимит `procurement.get` (50) не давал дочитать
остальное.

Нужно:

- считать listing фильтром retrieval (статус, один источник, исключающие
  слова, подстрочный шум), а не вердиктом;
- открывать карточку и считать `scoreSearchIntent` по title + лотам;
- писать совпадение в кабинет сразу, не ждать конца очереди;
- не стирать список при reload / смене вкладки — он из SQL по профилю;
- файлы по-прежнему только у «Участвовать»; 20 запросов/мин к площадке;
- кабинеты не смешиваются.

## 2. Архитектурное решение

```
procurement.search (фразы профиля)
  → listingKeepsPlatformHit (шум / исключённые слова)
  → очередь карточек, без match/discard по title
  → по одной: procurement.get → scoreIntentCard(title + lots)
       match     → SQL workspace_procurements, вкладка «Закупки»
       veto      → rememberIrrelevant этого профиля
       иначе     → входящие «На проверку»
  → GET /api/procurements/search/progress
       scoredCount / matchCount пока очередь жива
```

Кнопка «Поиск» отвечает после listing: `items` — очередь **этого** запуска,
`run` — счётчики. Фон дочитывает карточки без блокирующего спиннера.
~~Неиспользованные находки **не пишутся** в `workspace_procurements`: в SQL
только «Участвовать» / «Отслеживать» / корзина.~~ **Устарело (R44):** с
STAGE-66 и durable-модели R16 в SQL пишутся и карточки текущих очередей
поиска (`isPersistableCabinetCase`: решения + review-кандидаты + id из
`searchIdsByProfile`), иначе очередь не переживала бы рестарт. Не попадают
в SQL только строки, которые не вошли ни в одну очередь и не получили
решения. Смена вкладки держит список в сессии консоли; первый вход читает
список из SQL по профилю. Кнопка «Искать» заново открывает карточки
площадки и не считает старый кэш «не подходит» за текущий прогон. Если в
профиле явно выбран завершённый статус, поиск показывает такие строки во
временной очереди.

Без review-порта (fixture-тесты) title стоит вместо карточки: тот же
scorer, синхронный ответ. Живой путь всегда идёт через `procurement.get`.

Слежение профиля — тот же scorer, только для id, которых ещё нет в
кабинете. Уже решённые не открываются повторно: `monitorDecidedCases`
ходит по сохранённым id, а не по «дата сдвинулась».

`REVIEW_ALGORITHM_VERSION = search-review-v4` — старые title-вердикты
не переиспользуются.

20 req/min уже стоят в `GoszakupkiHttpClient` по умолчанию; карточки
открываются по одной, чтобы не обходить лимит пачкой.

Общая таблица `procurements` и хеш в MinIO остаются общими. Список и
inbox — `workspace_procurements`. Второй кабинет, найдя ту же процедуру,
всё равно читает `/view/` (лоты не лежат в shared-строке), но blob по
хешу не качает второй раз.

## 3. Почему так

Вердикт по строке списка врал: площадка матчит лот, адаптер видит только
заголовок. Ждать все get перед ответом — минуты и пустая вкладка.
Стереть список в localStorage — после reload пропадали уже найденные
match. Оценка в коде (`scoreSearchIntent`), модель только если карточка
не закрыла случай.

## 4. Изменённые файлы

- `packages/contracts/src/specialist.ts` — `SpecialistSearchRun`, `run` в
  ответе поиска
- `packages/domain/src/search/evaluate.ts` — метрики «new» после listing-фильтра
  и `scoreSearchIntent`, а не match из строки списка
- `packages/domain/src/specialist/workspace.ts` — `search-review-v4`
- `apps/api/src/search-progress.ts` — in-memory прогресс по профилю
- `apps/api/src/app.ts` — score после get, persist каждой match,
  `GET /api/procurements/search/progress`, discovery только новых id;
  завершённые без triage не persist, prune снимает их из SQL
- `packages/domain/src/specialist/catalog.ts` — prune закрытых undecided
- `apps/web` — список из SQL, полл прогресса, без wipe localStorage
- тесты: listing не вердикт; фон пишет match по одной; reload не пустой;
  завершённая без «Участвовать»/«Отслеживать» не остаётся в кабинете

## 5. БД и контракты

Миграций нет. `SpecialistSearchResponse.run` опционален — старые клиенты
игнорируют поле.

## 6. Тесты

- listing с intent: все живые строки → review-очередь, discard только
  фильтры профиля;
- без review-порта title-score совпадает с карточкой без лотов;
- с review-портом POST сразу `items: []` + `run.status = retrieving`,
  затем GET списка содержит match после каждой карточки;
- discovery не переоткрывает уже известный id;
- вкладка «Закупки» после remount показывает сохранённые карточки
  профиля, а не пустой экран.

## 7. Проверка

`npm run verify`

## 8. Риски

- Первый проход длинный: 20 карточек/мин. Прогресс и растущий список —
  единственная обратная связь; оборвать очередь пока нельзя.
- Title-only fixture не видит лот — live без `searchReview` в API не
  должен оставаться (production всегда подключает MCP get).
- In-memory progress сбрасывается с процессом; после рестарта API во
  время поиска список уже в SQL, счётчик — нет. Повтор «Искать»
  дочитывает только неизвестные id.
