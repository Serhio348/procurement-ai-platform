# Этап 66 — очередь поиска живёт по профилю, пока её не разберут

## Цель

После поиска по одному профилю смена на другой затирала очередь: прогресс
застывал на 100%, вкладка «Закупки» показывала чужой прогон, а при возврате
карточек уже не было. Нужно хранить неразобранный поиск отдельно по каждому
профилю и не удалять его, пока специалист не примет решение.

## Архитектурное решение

1. `searchIdsByProfile` больше не вырезается при записи. Он уходит в JSON
   кабинета и в `workspace_settings.settings`.
2. В SQL попадают не только решения и review, но и карточки текущих очередей
   поиска (`isPersistableCabinetCase`).
3. Новый поиск по профилю не обнуляет очередь: совпадения дописываются,
   «Отслеживать» / «Участвовать» / «Не нужно» снимают карточку.
4. Смена профиля активирует его и читает `GET ?tab=search` + прогресс этого
   профиля. Карточки других профилей в состоянии консоли не выкидываются.
5. Полоска процента при новом листинге начинается с 0 и не берёт 100% от
   законченного прогона другого профиля.
6. Фон и кнопка не пропускают чужое совпадение как «уже есть»: карточку
   дочитывают заново, если её нет в очереди этого профиля. Отсев снимает
   только свою очередь; чужое решение и чужая очередь остаются.

## БД

Миграции нет: очередь пишется в уже существующий JSON `settings`.

## Тесты

- очередь переживает перезапуск с диска;
- поиск Кабель → поиск КТПБ → снова Кабель: вкладка search снова «Поставка кабеля»;
- завершённая найденная карточка остаётся в очереди, пока её не разобрали;
- новый листинг не показывает 100% прошлого прогона;
- фон кладёт общее совпадение во вторую очередь и не стирает первую;
- отсев фона по второму профилю не удаляет карточку из очереди первого.

## Риски

- Очереди копятся, пока специалист не разберёт карточки. Это сознательно.
- Повторный поиск по тому же профилю добавляет, а не заменяет список.
