# Этап 67 — отклонённые «На проверку» больше не возвращаются во входящие

## Цель

После «Удалить» у строки «На проверку» фоновый поиск и повторный поиск с
кнопки снова клали ту же закупку во входящие. Специалист уже сказал «нет»:
повторно показывать её нельзя. Во входящие должны попадать только новые
совпадения и новые кандидаты.

## Архитектурное решение

1. Снятие `procedure_candidate` (DELETE inbox или resolve `dismiss`) пишется
   как `reject` по `sourceProcurementId`. Карточка уходит в корзину, из
   очереди поиска снимается.
2. `queueFoundInbox` не создаёт и не поднимает строку, если источник уже в
   `rejectedSourceIds`.
3. Для review-дубликата `undismiss` больше не вызывается: только «Новая
   закупка» может вернуться после снятия.
4. И кнопка поиска, и discovery вызывают `collectPendingHits` с
   `restoreReviewInbox: false` и `skipKnownIrrelevant: true` — отклонённые и
   уже разобранные review не переоткрываются.

## Почему так

Раньше dismiss хранил только id строки inbox. Следующий поиск находил тот же
change id и делал `undismiss`. Это выглядело как «оно само возвращается».
Решение специалиста должно жить на уровне источника закупки, как «Не нужно»
на карточке, а не на уровне одноразового id уведомления.

## Изменённые файлы

- `apps/api/src/app.ts` — `rememberDismissedReview`, фильтр в `queueFoundInbox`,

- `apps/api/src/app.test.ts` — dismiss review больше не восстанавливается
- `packages/domain/src/specialist/catalog.ts` — комментарий к `undismiss`
- `docs/architecture/STAGE-67.md`, `AGENTS.md`

## БД

Миграции нет: решение пишется в уже существующий журнал triage workspace.

## Тесты

- поиск → «На проверку» → «Удалить» → повторный поиск: inbox пуст;
- discovery по тому же источнику: inbox пуст;
- карточка лежит в корзине с `triage: reject`.

## Риски

- Ошибочное «Удалить» убирает источник до восстановления из корзины. Это
  сознательно и совпадает с «Не нужно».
- Старые dismiss без `reject` в журнале после деплоя не задним числом не
  помечаются: достаточно один раз снять строку снова.
