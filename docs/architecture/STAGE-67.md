# Этап 67 — решение по лотам не зависит от их порядка (R07)

## Цель

`scoreIntentProcedure` выбирал первый `explicit` результат через `.find` по
порядку клауз `[title, ...lots]`. Если первый подходящий по форме лот
оказывался `discard`/`veto` (например, НКУ для освещения при исключённом
освещении), следующий действительно подходящий лот (НКУ для насосов) уже не
рассматривался. Перестановка лотов меняла вердикт: `discard` ↔ `match`.

Цель: вердикт определяется наличием подходящего лота, а не его позицией.
Подходящий лот не должен скрываться неподходящим или сомнительным соседом.

## Архитектурное решение

1. Каждый лот по-прежнему оценивается **отдельной клаузой** через
   `scoreSearchIntent` — предметы разных лотов не склеиваются: объект из одного
   лота и действие из другого не образуют искусственное совпадение.
2. Лоты сортируются детерминированно по номеру перед оценкой — результат не
   зависит от порядка, в котором площадка отдала лоты.
3. Клаузы ранжируются по решению (`match` > `review` > `veto` > `discard`),
   внутри решения — по оценке. Выбирается сильнейший результат, а не первый:
   - явный `match` любого лота или заголовка побеждает;
   - иначе смешанный предмет (`peer`) остаётся на проверке;
   - иначе явный `review`;
   - иначе veto/implicit/discard по прежним правилам.
4. Причина выбранного лота получает префикс `Лот N: …` — в объяснении видно,
   на каком лоте основано решение.
5. `REVIEW_ALGORITHM_VERSION` → `search-review-v5`: автоматические вердикты
   «нерелевантно», выставленные порядкозависимым алгоритмом, пересматриваются
   при следующем поиске. Ручные решения специалиста не трогаются.

Веса и правила распознавания действий не менялись — это исправление выбора
результата, а не пересмотр скоринга.

## БД

Миграции нет. Версия алгоритма хранится в записи вердикта в JSON кабинета;
старые записи `search-review-v*` инвалидируются при чтении снапшота.

## Тесты

- оба порядка лотов «освещение/насосы» дают `match` по насосному лоту;
- смешанный первый лот + подходящий второй → `match`, а не `review`;
- подходящий лот + неподходящий сосед → `match` независимо от позиции;
- работа в одном лоте и поставка в другом не склеиваются в совпадение;
- причина содержит номер лота-основания;
- API: подходящий лот решается кодом без вызова модели;
- вердикты `search-review-v4` инвалидируются, ручные решения сохраняются.

## Приёмка

- Перестановка лотов не меняет вердикт и оценку — выполняется регрессиями.
- Подходящий лот не скрывается неподходящим первым — выполняется.
- Каждый лот остаётся независимым предметом — выполняется.
- Объяснение указывает лот-основание — префикс `Лот N:`.

## Риски

- Поднятие версии алгоритма заново отправляет на проверку карточки, ранее
  автоматически отброшенные. Это сознательно: часть из них была отброшена
  ошибочно по порядку лотов.
- Приоритет `match` над `peer` означает: если один лот смешанный, а другой —
  чистое совпадение, процедура считается подходящей. Смешанный лот при этом не
  исчезает из карточки и виден специалисту.
