# Этап 71 — дедупликация не прячет непрочитанные страницы площадки (R11)

## Цель

Бюджет выдачи делился **до** дедупликации: каждый терм получал
`max(20, ceil((offset+limit)/terms))` строк и останавливался, набрав свою
долю. Два терма с одинаковой первой страницей из 20 процедур при `limit=40`
возвращали 20 уникальных hits — вторые страницы не читались, а API вычислял
`hasMore: hits.length >= limit` → `false`. Кнопка «следующая страница»
исчезала, хотя источник не был исчерпан. Потолок 30 страниц также не
сообщался как усечение.

Цель: читать страницы непустых термов до бюджета **уникальных** кандидатов
и честно сообщать, остались ли у источника непрочитанные строки.

## Архитектурное решение

1. **Два прохода в адаптере.** Проход 1 — первая страница каждого терма:
   инвариант этапа 62 «каждая фраза — свой запрос» сохраняется, широкая
   фраза не может лишить остальных их доли. Проход 2 — round-robin по
   термам с `hasNextPage`, пока `unique.size < offset + limit`; потолок
   `MAX_SEARCH_PAGES_PER_TERM = 30` страниц на терм защищает от бесконечного
   сканирования.
2. **`hasMore` в `ProcurementSearchResponse`** (опциональный, контракт
   обратно-совместим): `true`, пока у хотя бы одного терма осталась
   непрочитанная страница — включая терм, остановленный потолком. Это
   ответ источника на «может быть ещё», а не эвристика по длине страницы.
3. **Прокладка через порт.** `SpecialistSearchHitsPort` получил опциональный
   `searchDetailed` — `{ hits, hasMore }`. Заглушки без него продолжают
   работать со старой эвристикой `hits.length >= limit`.
   `createProcurementSearchHits` реализует оба метода одним вызовом MCP —
   поле проходит `outputSchema` бесплатно.
4. **API.** `fetchProfileHits` объединяет флаги первичного и дополнительного
   поиска (`firstPage.hasMore || extraPage.hasMore`); `runManualSearch`
   отдаёт `hasMore || hits.length >= limit`.

## Результат

| Сценарий | Было | Стало |
|---|---|---|
| 2 терма, одинаковые первые 20, есть стр. 2, limit=40 | 20 hits, hasMore=false | 40 hits, hasMore=true |
| все термы исчерпаны | hasMore=false | hasMore=false |
| терм упёрся в потолок 30 стр. | молча усечено | hasMore=true |

## БД

Миграций нет. `REVIEW_ALGORITHM_VERSION` не менялся: изменён retrieval
(какие строки доходят до оценки), а не семантика вердиктов — старые
решения остаются корректными.

## Тесты

- два терма с общей первой страницей: адаптер дочитывает до 40 уникальных
  hits, общие строки получают `matchedSearchTerms` обоих термов,
  `hasMore: true`;
- все термы исчерпаны → `hasMore: false`;
- инварианты сохранены: каждая фраза — отдельный запрос; доля широкой
  фразы ограничена; dedup и provenance термов прежние.

## Приёмка

- Пересекающиеся термы не скрывают кнопку следующей страницы, пока
  источник не исчерпан.
- Потолок страниц сообщается как усечение через `hasMore`.
- Порядок merge между страницами стабилен: бакеты сортируются по
  убыванию id процедуры внутри терма, interleave — как раньше.

## Риски и ограничения

- Глубина чтения выросла: бюджет уникальных кандидатов может требовать
  больше страниц, чем раньше (запросов ≤ 30 на терм). Это и есть смысл
  исправления — раньше недобор маскировался короткой выдачей.
- `hasMore: true` означает «могут быть ещё»: непрочитанные страницы могут
  содержать одни дубликаты. Следующий запрос с большим offset перечитает
  страницы с начала — stateless-курсор как и раньше.
