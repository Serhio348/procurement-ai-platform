# Этап 72 — лимит обращений к модели соблюдается на прогон, а не на карточку (R13)

## Цель

`maxModelCalls` существовал и документировался как «число вызовов модели
на один поисковый прогон», но фактически не работал: счётчик
`modelCalls` был локальной переменной внутри `review(hits)`, а оркестратор
вызывал `review([hit])` по одной карточке в цикле — счётчик обнулялся на
каждой итерации. При `maxModelCalls=1` две неясные карточки давали два
вызова модели; при ста спорных — сто.

Цель: единый бюджет на прогон, общий для всех карточек; исчерпание видно
специалисту, а не тихое обрезание.

## Архитектурное решение

1. **`ReviewBudget { used: number }`** — явный общий счётчик. Владельцем
   выступает оркестратор: `scorePendingHits` создаёт `{ used: 0 }` один
   раз на прогон и передаёт в каждый вызов `review([hit], profile, budget)`.
2. **Порт обратно-совместим.** Третий параметр опционален — реализации
   `(hits, profile) => outcomes` продолжают удовлетворять сигнатуре,
   заглушки в тестах не тронуты. Без бюджета `review` ведёт себя как
   раньше (локальный счётчик на вызов).
3. **Исчерпание — не потеря.** `quotaOutcome` возвращает `needs_human` с
   причиной «Лимит проверок моделью за один поиск исчерпан — уточните
   ключевые слова профиля» — карточки попадают во входящие «На проверку»,
   а не отбрасываются.
4. **`DEFAULT_REVIEW_MAX_MODEL_CALLS = 50` не менялся.** Вынос значения в
   конфигурацию отложен до этапа локальной модели.

## БД

Миграций нет. `REVIEW_ALGORITHM_VERSION` не менялся: семантика вердиктов
не изменилась — изменилось только то, сколько карточек реально доходит до
модели.

## Тесты

- API: `maxModelCalls=1`, две неясные карточки через реальный
  `createProcurementSearchReview` → `classify` вызван ровно один раз,
  прогон доходит до `done` (ранее — два вызова).
- Юнит: бюджет внутри одного `review(hits)` уже был покрыт и сохранён.

## Приёмка

- Поиск со множеством спорных карточек не превышает заданное число вызовов
  модели — проверено через API, а не только прямым вызовом batch-review.
- Исчерпание бюджета видно специалисту как причина во входящих.

## Риски и ограничения

- Карточки сверх бюджета ждут ручной проверки — это штатная деградация,
  не потеря данных.
- Параллельные поиски разных профилей получают бюджет каждый — лимит
  по-прежнему «на прогон», а не глобальный. Глобальный лимит (на кабинет
  или окно времени) — осознанное расширение, если появится нужда.
