# Этап 73 — review-кандидат перепроверяется, а не воскрешается как есть (R05)

## Цель

`foundAs === "review"` хранит «не смогли решить», но обрабатывался как
окончательный вердикт. Ручной поиск при виде сохранённой review-карточки
просто возвращал старую строку во входящие — карточка и модель не
вызывались, временный сбой (модель недоступна, карточка не прочиталась)
становился постоянной ручной очередью. В discovery review-кандидат
пропускался вообще — причём без проверки, каким профилем он создан:
недоразобранная карточка профиля A навсегда блокировала её оценку для B.

Цель: сохранённый review-кандидат — это отложенная работа, а не ответ.
Он идёт обратно в `pending` и перепроверяется под текущим профилем.

## Архитектурное решение

1. **`collectPendingHits` без ветки восстановления.** Review-кандидат
   попадает в `pending` вместе с новыми неясными строками — в ручном
   поиске и в discovery. Опция `restoreReviewInbox` и счётчик
   `restoredReview` удалены; параметр `now` больше не нужен.
2. **Исходы перепроверки — штатные ветви `scorePendingHits`.**
   `relevant` → `foundAs: match`, очередь поиска, inbox-строка снимается;
   `irrelevant` → отказ фиксируется для профиля (`rememberIrrelevant`),
   чужой профиль не затрагивается; `needs_human` → карточка остаётся
   review-кандидатом.
3. **Возврат во входящие — только ручной поиск.** `queueFoundInbox` при
   `needs_human` вызывается и для существующей карточки (`!inboxForMatches`
   — ручной прогон), восстанавливая и отклонённую строку — паритет со
   старым поведением. Discovery (`inboxForMatches`) по-прежнему объявляет
   только новых кандидатов — фоновый проход не дёргает специалиста одной
   и той же карточкой каждый час.
4. **Профильная честность.** Перепроверка идёт под планом и контекстом
   текущего профиля; `rememberIrrelevant` и `attachProfileToCard` ключуются
   по `profile.id` — отказ одного профиля не портит кандидата другому.

## БД

Миграций нет. `REVIEW_ALGORITHM_VERSION` не менялся: семантика вердиктов
не изменилась — изменилось то, что отложенные кандидаты доходят до оценки
повторно.

## Тесты

- API: первый поиск → `needs_human` (модель недоступна), порт «выздоровел»
  → `relevant`; второй поиск вызывает проверку повторно, карточка
  попадает в очередь — раньше вызов был один суммарно.
- Инвариант сохранён: отклонённая review-строка возвращается во входящие
  при повторном ручном поиске.

## Приёмка

- Восстановление модели → новая проверка при следующем поиске.
- Поиск по другому профилю → оценка кандидата под его критериями, а не
  пропуск из-за чужого review.
- Недоступность модели не кэшируется как окончательный результат.

## Риски и ограничения

- Перепроверка стоит `procurement.get` (+ вызов модели в пределах
  бюджета) на каждый сохранённый review-кандидат за проход — discovery с
  сотней недоразобранных карточек будет тратить ресурс каждый цикл. Это
  честная цена: «отложенное» больше не маскируется под «разобранное».
- Полноценный кэш по версии плана/алгоритма и возрасту данных — часть
  R04/R12 (профильная проекция вердикта); здесь кандидат всегда
  перепроверяется — консервативно и безопаснее пропуска.
