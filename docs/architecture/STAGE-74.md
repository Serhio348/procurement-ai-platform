# Этап 74 — оценка card-level проверки доходит до карточки UI (R06)

## Цель

Listing-кандидат рождался с `relevanceScore: 0` и причиной-заглушкой
«карточка дочитывается». `scoreIntentCard` честно вычислял кодовую оценку
0–100 по прочитанной карточке площадки, но `ReviewOutcome` её не нёс, а
`scorePendingHits` обновлял только вердикт, причину и статус — в
сохранённой карточке навсегда оставался 0. Специалист видел «Оценка 0»
после настоящей проверки.

Цель: UI показывает оценку именно последней card-level проверки; число
пишет код, никогда модель.

## Архитектурное решение

1. **`ReviewOutcome.score?: number`** — кодовая оценка 0–100 оценённой
   карточки. `outcomeFromIntentCard` прикрепляет `scored.score` к обоим
   исходам (relevant/irrelevant) — оценка и вердикт рождаются одним
   вычислением.
2. **`createProcurementSearchReview`** прикрепляет `scored.score` ко всем
   исходам оценённой карточки — не только решение по карточке, но и ответ
   модели, квоту и недоступность. У `needs_human` тоже видна реальная
   оценка (например 60), а не заглушка 0.
3. **`scorePendingHits`** пишет `outcome.score` в `relevanceScore`
   сохраняемой карточки. Основание оценки уже присутствует в `reason`
   («Лот N: …», этап 67); статус прочитанной карточки проходит через
   `attachCardStatus` как раньше.
4. **Модель не назначает число.** `outcomeFromModel` не читает `score` —
   число приходит только из `SearchIntentScore`, вычисленного кодом.

## БД

Миграций нет: поле `relevanceScore` существует, заполняется при следующей
оценке. `REVIEW_ALGORITHM_VERSION` не менялся — семантика вердиктов
прежняя, изменилась только передача уже вычисленного числа.

## Тесты

- API: hit «Закупка НКУ» → карточка «Поставка НКУ для насосов» с лотом
  НКУ → `match`; сохранённый `relevanceScore` равен оценке
  `scoreSearchIntentFromProcedure` (100), не listing-нулю — раньше было 0.

## Приёмка

- UI показывает оценку последней card-level проверки, а не заглушку.
- Число — только кодовое: модель может изменить вердикт/причину, но не
  `score`.

## Риски и ограничения

- `needs_human` теперь показывает реальную (часто среднюю) оценку — это
  честнее нуля, но специалист может прочитать её как «почти подходит»;
  причина рядом поясняет, почему код не решился.
- Оценка одна на карточку: при оценке под разными профилями сохраняется
  число последней проверки — профильная проекция оценки остаётся
  территорией R04.
