# Этап 80 — «Открыть карточку» из inbox всегда открывает нужную закупку (R46)

## Цель

После этапа 79 открытие стало быстрым, но у элементов «На проверку» кнопка
«Открыть карточку» снимала строку inbox, а страница `/procurements/:id`
показывала **первую строку очереди** вместо нужной карточки — специалист её
«не находил».

## Коренная причина

Детальный маршрут выбирал карточку только из поисковой очереди:

```ts
const selected = items.find((item) => item.id === params["id"]) ?? items[0];
```

А очередь скрывает часть карточек намеренно:

1. **`withTriage` переносит прошлое решение.** `resolve` в API помечает
   карточку `latestKind(sourceProcurementId)` — если по этой закупке уже
   было решение `monitor`/`participate`/`reject`, `isSearchQueueCard` и
   `belongsToChosenProfile` исключают её из `searchPaneItems`. В проде с
   историей из ~139 решений это обычная ситуация.
2. **`uniqueBySource` дедупит по `sourceProcurementId`** — карточка-кандидат
   могла проиграть другой строке с тем же исходным номером.

Итог: `items.find(id)` промахивался, `items[0]` рисовал чужую карточку (или
пустоту), а inbox-строка была уже снята — «открывается и пропадает».

## Решение

Детальный маршрут ищет запрошенную карточку шире очереди:

1. **Полный каталог на `/procurements/:id`** — роут получает
   `items={procurements}` без фильтра search-pane; очередь по-прежнему
   фильтруется внутри `ProcurementsApp` (`isSearchQueueCard`,
   `belongsToChosenProfile`), так что список слева не изменился.
2. **Fallback-цепочка `selected`**: очередь → весь каталог → `fetchCase`.
   Карточка с любым triage-статусом или выкинутая дедупом всё равно
   находится по `params.id`.
3. **`fetchCase` (`GET /api/procurements/:id`) + `onCardLoaded`** — если
   карточки нет даже в состоянии (перезагрузка страницы, прямая ссылка),
   она подгружается по id и запоминается в `procurements`.

Открытие из inbox не является решением: карточка отображается с текущим
triage-состоянием и кнопками «Отслеживать» / «Участвовать» / «Не нужно» —
решение принимает специалист.

## Изменённые файлы

- `apps/web/src/procurements/ProcurementsApp.tsx` — fallback-цепочка
  `selected`, `fetchCase`/`onCardLoaded`, эффект загрузки по id.
- `apps/web/src/SpecialistApp.tsx` — `/procurements/:id` получает полный
  `procurements` и `loadCard`/`rememberCard`.
- `apps/web/src/procurements/ProcurementsApp.test.tsx` — регрессии.

## Тесты

- `opens a decided card aimed at by the inbox even though the queue hides
  it` — карточка с triage `monitor` вне очереди открывается по id и даёт
  все три кнопки решения.
- `fetches the inbox-opened card by id when nothing in state carries it` —
  отсутствующая в состоянии карточка подгружается через `fetchCase` и
  кладётся в каталог.
- Полный `verify`: 639 + 82 теста, типы/линт/архитектура зелёные.

## Приёмка

- «Открыть карточку» на любом элементе inbox (новая закупка, на проверку,
  изменение карточки) переводит на деталь именно этой закупки.
- Деталь показывает актуальное triage-состояние и все три решения; открытие
  само по себе не меняет вердикт.

## Риски и ограничения

- `foundAs: "review"` → `"match"` на `open` сохраняется (этап 27: «открыть
  = взять в работу»); изменение этой семантики — отдельное решение.
- Список слева не подсвечивает строку, которой нет в очереди — деталь
  показывает саму карточку, этого достаточно для решения.
