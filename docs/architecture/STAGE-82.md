# Этап 82 — слежение за сроком подачи: «истекает завтра» и «истёк»

## Цель

Фоновое слежение реагировало только на изменения **полей** карточки:
`diffCardSnapshots` сравнивает статус, цену, текст дедлайна и документы.
А «срок подачи истёк» — это прохождение времени: значение `bidsDeadline`
на площадке не меняется, и статус «приём заявок» площадка может держать
неделями после закрытия окна. Diff возвращал пусто — во входящих не было
ни события, ни предупреждения.

## Решение

Дедлайн оценивается по **времени**, а не по diff'у полей.

### Домен — `packages/domain/src/specialist/deadline.ts`

- `deadlineInstant(card)` — эффективный момент закрытия: сначала
  `sourceCard.bidsDeadline`, затем `watchSnapshot.bidsDeadline`
  (date-only → `{precision: "date", timeZone: "Europe/Minsk"}`).
- `deadlineCrossedSince(card, capturedAt, now)` — дедлайн был в будущем
  на момент прошлого снимка и стал прошедшим сейчас. Одно срабатывание:
  следующий снимок уже «после», поэтому повторных событий нет.
- `deadlineWithin(card, now, windowMs)` — до закрытия осталось меньше
  окна (36 ч). Для date-only считается календарная дистанция в поясе
  источника: «завтра» ≈ внутри окна, «послезавтра» — нет; выдуманного
  времени суток нет.
- `bidsDeadlinePassed` сохранён как есть.

### API — `monitorDecidedCases` в `apps/api/src/app.ts`

После обычного diff, если сам `deadline_changed` уже не зафиксирован
полем (реальная смена даты покрывает оба случая):

- **«срок подачи истёк»** — `deadlineCrossedSince` для monitor и
  participate; на первом проходе без снимка — `bidsDeadlinePassed`,
  чтобы карточка, взятая под слежение уже просроченной, сообщилась один
  раз. Триггер — переход «вперёд → позади», статус «приём заявок» на
  странице его не глушит.
- **«срок подачи истекает завтра»** — только `triage === "participate"`,
  `deadlineWithin(now, 36h)`. Monitor-only карточки предупреждением не
  шумят.

Оба идут через `inboxItemFromWatchChange` как `deadline_changed` с
`current` = текст фазы — ID события
`inbox-watch:{card.id}:deadline_changed:{фаза}` стабилен, поэтому
повторные проходы внутри окна не плодят строки: `catalog.record`
дедупит по ID. «Истёк» и «истекает завтра» — разные `current` → две
разные строки, как и задумано.

### Web — `apps/web/src/SpecialistApp.tsx` + `shell/NoticeToast.tsx`

- `NoticeStack` — пассивные тосты в правом нижнем углу, `role="alert"`,
  автозакрытие через 10 с, крестик. `ConfirmToast` не подходил — он
  модальный, с backdrop и решением.
- `applyInboxItems` — единая точка подмены inbox: запоминает увиденные
  ID (`knownInboxIds`, засеян начальным списком → первая загрузка
  молчит), и каждая **новая** строка `kind === "deadline_changed"`
  поднимает тост «{заголовок закупки} — {summary}». Повторный poll с
  той же строкой тоста не даёт. Все `refreshInbox` — 30-секундный poll,
  поиск, решение, resolve — идут через эту функцию.

Строка во входящих остаётся durable-копией: тост исчезает, запись
«Срок подачи: X → срок подачи истёк» открывается как обычно.

## Регрессии

- `deadline.test.ts` — переход через дедлайн, повторное молчание, окно
  <36 ч по точному и по date-only дедлайну (Europe/Minsk), отсутствие
  дедлайна.
- `app.test.ts` — «истёк» при «приём заявок» на странице, один раз, без
  дублей; «истекает завтра» только у participate, monitor-only молчит.
- `SpecialistApp.notice.test.tsx` — молчание на первом рендере, тост из
  poll, без повтора, обе фазы различимы.
