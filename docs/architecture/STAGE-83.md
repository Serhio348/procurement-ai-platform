# Этап 83 — очередь поиска и живой прогресс восстанавливаются после reload (R01)

## Цель

Сохранённая сервером поисковая очередь профиля (этап 66) показывалась
только после повторного выбора профиля: `LiveConsole` передавал
`procurements: []`, а `SpecialistApp` ничего не читал при монтировании.
Обновление страницы или возврат после перезапуска браузера показывали
пустую вкладку «Закупки», хотя на сервере очередь жива; запущенный поиск
тоже не подхватывался — polling прогресса стартует только когда
`searchRun` уже установлен.

## Решение

Mount-эффект в `SpecialistApp` при первом рендере выполняет ту же
загрузку, что и `openProfileSearch` при смене профиля:

- `listMine({ tab: "search", limit: 400 })` → `mergeSearchPane` —
  восстанавливает очередь активного профиля поверх текущего состояния
  (отслеживаемые и отклонённые карточки сохраняются);
- `searchProgress()` → `setSearchRun` — если поиск ещё идёт
  (`retrieving`/`scoring`), установленный `searchRun` автоматически
  запускает существующий 800-мс polling: прогресс и очередь
  продолжают обновляться без нового запуска поиска.

Ошибки загрузки глотаются так же, как при смене профиля: уже показанные
карточки остаются.

## Регрессии

- `restores the stored search queue on mount without running a search` —
  карточка очереди видна сразу, `search` не вызывался;
- `resumes polling a still-running search after a page reload` —
  `searchProgress` вызывается повторно по таймеру после восстановления
  `searchRun`.
