# Этап 86 — целостность записи кабинета (R18–R21, R26)

Кластер из пяти пунктов ревью, сделанный одной серией: все они
опираются на один вопрос — «какая запись кабинета настоящая и кому
видна её ошибка». Порядок работ: сначала система записи выбирается
явно (R20), затем persist перестаёт скрывать сбои (R19), один кабинет
становится одним объектом (R26), записи перестают рваться (R21), и
поверх этого inbox может честно подтверждать приём события (R18).

## R20 — система записи выбирается явно

Раньше заданный, но недоступный `DATABASE_URL` (или отсутствующая
схема) молча переводил API на файлы и `createMemoryAuthDirectory` —
под тем же адресом обслуживался другой набор пользователей и пустые
кабинеты.

Теперь непустой `DATABASE_URL` делает PostgreSQL обязательным:
`openSpecialistPersistence` бросает ошибку и процесс не стартует.
Сообщения различают причины: «PostgreSQL недоступен» (нет
подключения) и «схема specialist отсутствует, npm run db:migrate»
(подключение есть, таблиц нет). Файловый режим с memory-auth остаётся
только при пустом `DATABASE_URL` — dev, CI и fixture-запуски.
`/api/health` отдаёт `postgres: true|false`, чтобы видеть, на чём
живёт процесс.

## R19 — persist говорит правду вызывающему

`persistWorkspace`, `persistCases`, `persistInbox`, `cabinets.persist`
и `persistProgress` ловили ошибку PostgreSQL, писали её в журнал и
возвращали успех — при том, что следующее чтение идёт из PostgreSQL.

Теперь в PostgreSQL-режиме ошибка записи журналируется и
пробрасывается вызывающему: эндпоинт отвечает 500 вместо ложного
«сохранено», фоновые задачи помечают прогон `failed` через свои
существующие catch. JSON-файлы в этом режиме — диагностическое
зеркало (`mirrorToDisk`, best-effort): их сбой логируется, но запрос
не валит — и наоборот, сбой PostgreSQL больше не маскируется дисковой
копией. В файловом режиме ошибки диска пробрасываются — это
единственная запись.

## R26 — один кабинет, один объект

`openCabinet` клал объект в cache после await загрузки: два первых
конкурентных запроса получали разные экземпляры кабинета, и их
записи гонялись. Кэш теперь хранит `Promise<SpecialistCabinet>` —
промис попадает в map до await, все конкурентные открытия делят один
объект. При ошибке загрузки промис удаляется — повтор возможен.

## R21 — записи не рвутся и не переупорядочиваются

- `writeJson` и `saveWorkspaceFile` пишут через `tmp-*` + `rename`:
  оборванная запись оставляет предыдущий целый файл вместо половины
  JSON, ломающей следующий запуск.
- `loadWorkspace` читает журнал решений с `ORDER BY made_at, id` —
  `latestKind` больше не зависит от плана запроса PostgreSQL.
- PostgreSQL-запись кабинета уже была одной транзакцией
  (`saveCabinet`: workspace + cases + inbox под advisory lock);
  внутрипроцессные гонки закрыты per-cabinet write-tail
  (`enqueueWorkspaceWrite`) и single-flight открытием (R26).

## R18 — 201 означает «записано»

`POST /api/inbox/events` записывал событие только в память и отвечал
201 — событие исчезало при рестарте, если до него не случилась
другая запись кабинета. Теперь `persist()` вызывается до ответа;
сбой хранилища возвращает 500. Дедупликация по `change.id`
(`catalog().record` → `duplicate` → 200) остаётся идемпотентным
ключом поставки.

## Ограничения

- Атомарность «три файла разом» на файловой системе недостижима —
  настоящая граница атомарности это PostgreSQL-транзакция; файлы
  остаются офлайн-fallback и диагностическим зеркалом.
- Два отдельных API-процесса по-прежнему держат собственные
  in-memory снимки кабинета (multi-instance deployment) — нужна
  версия состояния/инвалидация кэша, это за рамками кластера.
- Стоимость записи по-прежнему растёт со всем кабинетом — это R37.
