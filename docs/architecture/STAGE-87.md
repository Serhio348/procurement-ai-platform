# Этап 87 — события мониторинга: единый diff, identity перехода, честное закрытие (R22, R23, R25)

Три пункта ревью про один механизм: как изменение на площадке становится
строкой входящих и что происходит, когда специалист эту строку закрывает.

## R22 — применение живой карточки само считает diff

Раньше события создавал только цикл `monitorDecidedCases`. Все остальные
пути чтения живой карточки (`GET /card?fresh=1`, гидратация при решении,
скоринг, reindex) звали `applySourceCard` — baseline мониторинга
подменялся молча, и следующий watch-tick изменения уже не видел:
уведомление о новом сроке или отмене могло быть «съедено» обычным
просмотром карточки.

Теперь всякое применение живой карточки идёт через
`applyFreshSourceCard`: `applySourceCard` + `diffCardSnapshots` + запись
событий — независимо от того, кто прочитал источник. Просмотр не
отменяет уведомление, а сам его создаёт.

Порядок в decision-эндпоинте при этом важен: сначала
`dismissByProcurementId` снимает старые строки карточки, затем живое
чтение создаёт свежие события. В обратном порядке свежее событие
снималось вместе со старыми (два регрессионных теста это и поймали).

## R23 — event id различает вхождения перехода

`catalog().record` дедуплицирует по `change.id`, который строился из
карточки, kind и текущего значения. Цикл `100→90→100→90` давал второму
«90» тот же id, что и первому — реальный переход проглатывался навсегда.

У `WatchChange` появился `dedupeKey` — токен вхождения:

- переходные diff'ы (статус, цена, срок) несут `capturedAt` нового
  снимка: возврат к прежнему значению — это новое событие;
- документные diff'ы несут `capturedAt:url`: два файла с одинаковым
  именем по разным ссылкам получают разные события;
- state-пуши дедлайна («срок истёк», «истекает завтра») ключа не имеют —
  их id стабилен, и повторные проходы не плодят строки.

`inboxItemFromWatchChange` включает ключ в event id и остаётся
единственной политикой identity событий мониторинга. Повторная доставка
того же применения по-прежнему дедуплицируется.

## R25 — строка закрывается только после успешного действия

Два дефекта в `POST /api/inbox/:id/resolve`:

- **Ошибка скачивания закрывала сообщение.** Ingest падал, ошибка
  журналировалась — и строка всё равно снималась с успешным ответом.
  Теперь сбой возвращает `502 ingest_failed`, строка остаётся во
  входящих — специалист видит ошибку (клиент уже бросает «Не удалось
  обработать сообщение») и может повторить.
- **«Обновить» применял историческое событие.** Строка хранит change,
  обнаруженный когда-то; к моменту нажатия площадка могла уйти дальше.
  Теперь `refresh` перечитывает живую карточку через `cardWatch` и
  применяет её общим путём (R22). Ошибка чтения → `502 refresh_failed`,
  строка остаётся. Без подключённого источника (fixture/offline) —
  прежнее поведение: событие строки применяется к карточке.

При живом обновлении переход, который описывала закрываемая строка,
переобнаруживается — и без подавления порождал бы строку-дубликат
(новый `dedupeKey` → новый id). `watchTransitionKey` (`kind:previous:
current`, без метки времени) подписывает логический переход:
`applyFreshSourceCard` принимает `suppressTransitions` — значения
перехода применяются к карточке, но событие не записывается. Поля,
ушедшие дальше закрытого события (например, цена изменилась ещё раз),
создают новую строку — это подлинно новое изменение.

## Ограничения

- Подавление по `kind:previous:current` не различает два одинаковых
  перехода разных полей документов с совпадающими именами — краевой
  случай, принят осознанно.
- R24 (замена файла по тому же URL) не входит в этап: diff видит
  `sourceUrl`/`name`, содержимое не хешируется — нужен отдельный
  механизм условного чтения с бюджетом.

## Регрессии

- `app.test.ts`: `reports a platform change when the card was opened
  before the watch pass` (R22); `refresh re-reads the live card,
  consumes its own row and reports further moves`, `keeps the inbox
  row when the live re-read for refresh fails`, `keeps the inbox row
  when the document download fails` (R25).
- `watch.test.ts`: возврат к прежнему значению — новое событие; два
  файла с одним именем — разные события; повторное применение того же
  снимка — дедуп (R23).
