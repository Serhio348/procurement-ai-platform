# Этап 89 — полнота списков, защита авторизации и честный evaluation (R27, R38–R40)

Четыре пункта ревью про доверие к тому, что показывает система: список
должен содержать все записи, а не первые сто; авторизация не должна
принимать неограниченный перебор; инвариант «хотя бы один админ» обязан
держаться под конкуренцией; оценка качества поиска должна мерить тот же
конвейер, который работает в production.

## R27 — серверная пагинация доходит до UI

`fetchProcurements` возвращал только `items`, отбрасывая
`total/hasMore`, поэтому «Мои закупки», архив и корзина обрезались
первой сотней, а очередь поиска — первыми 400 строками. Теперь клиент
сохраняет метаданные страницы, а `SpecialistApp.loadEntireList`
дочитывает все страницы через `limit`/`offset` по `hasMore` — для
кабинетных вкладок и для очереди поиска (восстановление после reload и
polling по завершении прогона).

«Загрузить ещё» в поиске остаётся источниковым запросом следующего
offset — это разные оси: просмотр накопленного и поиск новых
кандидатов. В корзине подтверждение очистки показывает полный объём
(`total`), а поиск по загруженному списку позволяет найти карточку
без прокрутки сотен строк.

## R38 — лимиты на перебор

Новый `RateLimiter` (`apps/api/src/auth/rate-limit.ts`) — скользящее
окно с двумя независимыми бюджетами: по источнику (IP) и по аккаунту
(email). Sign-in, sign-up и forgot-password возвращают 429 при
исчерпании любого из них; успешный вход очищает ключ аккаунта, чтобы
опечатки не висели на пользователе. Forgot-password троттлится по
адресу с тем же ответом, что и для несуществующего аккаунта —
существование не раскрывается.

Вторая линия — в `infra/nginx/procurement.conf`:
`limit_req_zone procurement_auth` (6 r/m, burst 10, `nodelay`) на
auth-маршрутах; приложение остаётся корректным и без nginx.

## R39 — атомарная проверка «последний админ»

`replaceStatus` читал всех пользователей и обновлял строку раздельно:
два конкурентных запроса могли оба пройти проверку и снять двух
последних администраторов. Теперь чтение-проверка-запись идут в одной
транзакции с `FOR UPDATE` — изменения админского состава
сериализуются, второй запрос видит уже применённое состояние и
получает `AuthConflictError("last_admin")`. Покрытие — интеграционный
тест под `TEST_DATABASE_URL`; memory-каталог не менялся.

## R40 — evaluation гоняет тот же pipeline

Harness оценивал `scoreSearchIntent(title, extraText)` и превращал
plain discard карточки в финальный отказ, хотя runtime отправляет
неразрешённую строку модели/человеку. Теперь `evaluateSearch` повторяет
production-конвейер `scorePendingHits`:

1. Листинг (`selectRelevantSearchCards`) — только retrieval.
2. Не отброшенные строки оцениваются `scoreIntentCard` на синтетической
   `ProcedureCard` (`procedureCardFromEvalCase`) — тем же агрегатором
   лотов, что работает после `procurement.get`.
3. Неразрешённое уходит в `SearchEvalReviewer` (по умолчанию
   `needs_human` → «review»), как в реальный порт модели.

`SearchEvalCase` получил `lots`; в корпус добавлены регрессии
R07/R08/R61: объект только в лоте, второй лот выигрывает независимо от
порядка, работы-предмет и «включая поставку» отбрасываются вето.
Отчёт разделяет retrieval recall, шум, дошедший до card-стадии, и
стадию решения (`listing/card/model`) — 100% на одном корпусе читается
как «на этом корпусе», а не как качество всей платформы.

## Ограничения

- `RateLimiter` — in-memory: на нескольких репликах API бюджеты
  делятся. Redis-реализация — отдельная задача при горизонтальном
  масштабировании.
- Интеграционный тест R39 требует `TEST_DATABASE_URL`; без PostgreSQL
  он пропускается, как остальные DB-тесты (см. R41).
- Evaluation по-прежнему без живого procurement.get: карточки
  синтетические из размеченных лотов; корпус — одно направление.
