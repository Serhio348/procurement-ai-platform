# Этап 91 — честные состояния списков: ошибка ≠ пустой кабинет (R28)

До этапа `MyProcurementsApp` в `catch` загрузки ставил `[]` — 500 или обрыв
сети отрисовывался как «Корзина пуста». Ошибки archive/remove/restore/purge
откатывали UI молча: карточка возвращалась без объяснения. Polling inbox и
прогресса поиска глотал сбои каждые 800 мс — экран старел без индикатора.
Стартовая загрузка в `main.tsx` теряла причину и не имела retry.

## Что изменилось

**Типизированная ошибка API.** `apps/web/src/api/http.ts` добавляет
`ApiError` (поля `status`, `code` из тела `{error}`) и `throwApiError` —
все `!response.ok` в `api/specialist.ts` теперь бросают её. Promise
rejection остаётся контрактом клиента; union «данные | ошибка» не введён.
`errorText(error, fallback)` — единая точка получения человеческой причины.

**Автомат состояния списка.** Каждая вкладка («Все», «Слежу», «Участвую»,
«Архив», «Корзина») хранит своё состояние:

```
loading → ready(items, updatedAt)
        → error(message)                — первый заход, данных ещё нет
ready   → stale(items, message, updatedAt) — обновление упало, данные остаются
```

`empty` — не состояние, а производная `ready.items.length === 0`. 500 при
первой загрузке показывает причину и «Повторить»; сбой при повторном заходе
на вкладку оставляет карточки и жёлтую плашку «Список не обновился… данные
от HH:MM» с кнопкой повтора.

**Защита от гонок.** Каждый запуск загрузки получает generation id; ответ
или ошибка применяются только если generation ещё актуальна. Переключение
вкладки делает поздний ответ предыдущей вкладки безобидным.

**Видимые ошибки действий.** Оптимистичный rollback сохранён, но теперь
неудача показывает баннер «Не удалось сохранить изменение: …», карточка
остаётся на месте, успешный повтор снимает баннер. Блокировка — по ключу
`itemId:operation`: во время «Вернуть» кнопка «Удалить» той же карточки и
кнопки соседних карточек остаются активными.

**Здоровье polling.** Счётчик подряд идущих сбоев по каналам `inbox` и
`run` (прогресс поиска + очередь). После трёх сбоев поднимается общая
плашка «Нет связи с сервером — показанные данные могут быть устаревшими»;
первый успешный poll канала снимает её. Показанные данные не стираются,
тостов на каждый 800-мс тик нет — только стабильный индикатор.

**Стартовая загрузка.** `LiveConsole` хранит `{error: message}` вместо
безликого `"offline"`; «Повторить» зовёт тот же `loadInitialData()`, что и
первый маунт — без перезагрузки страницы.

## Границы

- Индикатор связи общий для консоли; направление «нет связи, показанные
  данные старые» не привязано к конкретной вкладке.
- Ошибки действий в `ProcurementsApp`/`ProfileApp` по-прежнему идут
  наружу как rejection — всплывающий баннер R28 покрывает списки
  «Мои закупки»/корзину; единый error boundary для остальных экранов —
  отдельный пункт.
- `openProfileSearch` при сбое загрузки очереди оставляет уже показанные
  карточки без пометки — поведение осознанно тихое: смена профиля не
  должна орать об ошибке фоновой подгрузки.
